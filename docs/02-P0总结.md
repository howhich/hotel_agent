## 2. 核心机制详解

### 2.1 左闭右开（`BookingServiceImpl:548` / `:565`）

```java
private void validateRange(LocalDate checkIn, LocalDate checkOut) {
    if (!checkIn.isBefore(checkOut)) throw BusinessException.badRequest("离店日期必须晚于入住日期（区间左闭右开）");
    ...
}

/** 展开入住区间 [checkIn, checkOut) 的每一天 */
private List<LocalDate> stayDates(LocalDate checkIn, LocalDate checkOut) {
    List<LocalDate> dates = new ArrayList<>();
    for (LocalDate d = checkIn; d.isBefore(checkOut); d = d.plusDays(1)) {   // ← isBefore，不是 !isAfter
        dates.add(d);
    }
    return dates;
}
```

**全项目只有这两处实现区间语义** —— 下单、算价、扣库存、释放、超时，全都调用它们。这样就不可能"某处多算一天"。

验证证据：订 10/12→10/15，台账里只有 **10/12、10/13、10/14** 三行。

### 2.2 逐天条件 UPDATE（`RoomInventoryMapper:38`）

```sql
UPDATE room_inventory SET sold_rooms = sold_rooms + #{n}, version = version + 1
WHERE room_type_id = #{roomTypeId} AND stay_date = #{stayDate}
  AND sold_rooms + #{n} <= total_rooms        -- ★ 条件写在 WHERE 里
```

**"够不够"和"扣减"在同一条语句里完成**，靠数据库行锁保证原子性。调用方只看影响行数：

```java
int updated = roomInventoryMapper.tryOccupy(dto.getRoomTypeId(), d, roomCount);
if (updated == 0) {
    throw BusinessException.conflict(d + " 房量不足，请调整日期或间数");
}
```

> **这就是"条件的判定与执行不可分离"** —— 如果先 `SELECT` 判断再 `UPDATE`，两步之间就有窗口期，两个并发请求会同时通过判断，造成超卖。把条件塞进 `WHERE` 就不存在这个窗口。

### 2.3 为什么不需要手写补偿（`createBooking:187`）

```java
@Transactional(rollbackFor = Exception.class)     // ← 关键在这一行
public Long createBooking(CreateBookingDTO dto) {
    ...
    for (LocalDate d : dates) {
        roomInventoryMapper.insertIgnore(...);
        int updated = roomInventoryMapper.tryOccupy(...);
        if (updated == 0) {
            throw BusinessException.conflict(...);   // 抛异常 = 让整个事务回滚
        }
    }
    ...
}
```

住 5 晚就要扣 5 天，如果第 4 天不够，**前 3 天已经扣掉了**。这里**没有写任何"把前 3 天加回去"的补偿代码** —— 因为 `@Transactional` 会让整个事务回滚，前 3 天的 UPDATE 自然被撤销。

验证证据（超卖测试）：订 3 间成功后，再抢第 4 间失败，此时库存**仍然精确是 2 天 × 3 间 = 6**，没有任何半占残留。

> **对比 TaxiAgent**：它是"抢单个司机"，失败只需把一个值设回哨兵；这里是"占 N 天"，手写补偿会非常容易漏，所以必须依赖事务。

### 2.4 台账释放：先标记，再还库存（`releaseInventory:414`）

```java
List<BookingInventoryLink> links = linkMapper.selectUnreleased(bookingId);
for (BookingInventoryLink link : links) {
    int marked = linkMapper.markReleased(link.getId());   // ★ 带 released=0 前置条件
    if (marked == 0) {
        continue;                                          // 已被别的流程释放过，跳过
    }
    int released = roomInventoryMapper.release(...);       // 只有抢到标记的人才能还库存
    if (released == 0) {
        log.error("库存释放异常（台账与库存不一致）: ...", ...);
    }
}
```

```sql
-- BookingInventoryLinkMapper.markReleased
UPDATE booking_inventory_link SET released = 1, release_time = NOW()
WHERE id = #{id} AND released = 0        -- ★ 抢占式
```

**顺序不能颠倒**。如果先还库存再标记，两个并发流程会各还一次 → 库存被加回去两遍 → 凭空多出房间。

这里的 `released = 0` 前置条件和 TaxiAgent 的**「一次性令牌」**是同一个思路：**让数据库来决定"谁抢到了这一次操作"**，而不是靠应用层判断。

终态证据：所有 `released=0` 的台账行汇总后，与 `room_inventory.sold_rooms` **逐行相等**。

### 2.5 状态流转也是条件 UPDATE（`BookingMapper`）

```sql
-- markPaid: 10 -> 20
UPDATE booking SET booking_status = 20, paid_amount = ?, pay_time = NOW(), update_time = NOW()
WHERE booking_id = ? AND booking_status = 10 AND is_deleted = 0
```

```java
int updated = bookingMapper.markPaid(bookingId, b.getTotalAmount());
if (updated == 0) {
    throw BusinessException.conflict("订单状态已变化，请刷新后重试");
}
```

**读到的状态不作准，UPDATE 打中几行才算准。** 影响 0 行说明状态在我们读取之后被别人推进了。

验证：重复支付、重复取消都返回 **409**，没有产生第二条状态变更。

> 注意 SQL 里显式写了 `is_deleted = 0`。MyBatis-Plus 的 `@TableLogic` **只对它自己生成的 SQL 生效**，手写 `@Update` 必须自己带上。

### 2.6 取消政策快照（`parseSnapshot:437`）

下单时把当时的规则**冻结**进订单（`CancelPolicy.snapshotJson()`）：

```json
{"policy":1,"name":"免费取消","tiers":[{"minHoursBefore":0,"refundRatio":"1.000"}]}
```

退款时**读快照，不读当前枚举**：

```java
private SnapshotPolicy parseSnapshot(String json) { ... }   // 用 Jackson 解析

BigDecimal ratio = snap.refundRatio(hoursBefore);
BigDecimal refund = paid.multiply(ratio).setScale(2, RoundingMode.HALF_UP);
```

**为什么要这样**：如果读当前枚举，那么改一次政策、发一次版，**所有历史订单都会被追溯适用新规则**。用户会投诉"我下单时不是这么说的"。

> **硬编码枚举 ≠ 可以不做快照**，这是两件独立的事。

验证：RT2002（限时免费）在距入住 32 小时时取消 → 命中 `>=24h` 档 → 退 50%（1000 → 500）。

### 2.7 惰性建库存行（`RoomInventoryMapper:22`）

```sql
INSERT IGNORE INTO room_inventory (room_type_id, stay_date, total_rooms, sold_rooms, version)
VALUES (?, ?, ?, 0, 0)
```

库存日历**不预先铺满**，用到哪天建哪天，靠 `UNIQUE(room_type_id, stay_date)` 保证并发下只成功一次。

配套要点：`checkAvailability` 遇到**没有库存行**时，按 `room_type.total_rooms` 当成"满房可订"，而不是当成 0 间 —— 这正是第 5 节①修掉的那个 bug。

> 生产环境的做法通常是**定时任务提前物化未来 N 天的库存**（酒店的"房态"）。P0 先用惰性建行，P2 的定时任务会补上。

## 3. 一次下单的完整调用链

```
POST /booking  {"userId":9001,"hotelId":1001,"roomTypeId":2001,
                "checkIn":"2026-10-12","checkOut":"2026-10-15","roomCount":1}
   │
   ▼  BookingController.create()                            :44
   │     @Valid 校验请求体
   ▼  BookingServiceImpl.createBooking()   @Transactional   :187
   │
   ├─① validateRange(10/12, 10/15)                           :548   区间合法？
   ├─② requireRoomType(2001)                                 :528   房型存在且在售？
   ├─③ hotelMapper.selectOne(...)                                  酒店存在？
   ├─④ quotePrice(...)                                       :140   算钱，缺价格日历就在这拦下
   │      roomPriceMapper.selectRange(2001, 10/12, 10/15)
   │      → 3 × 400 = 1200
   ├─⑤ IdWorker.getId()  → bookingId（雪花）
   │
   ├─⑥ for (d : [10/12, 10/13, 10/14])        ★ 逐天占库存
   │      roomInventoryMapper.insertIgnore(2001, d, 3)
   │      updated = roomInventoryMapper.tryOccupy(2001, d, 1)
   │      if (updated == 0) throw 409 ────────┐
   │                                          │ 任何一天失败
   ├─⑦ for (d : 同上)  写 3 行台账             │ → 抛异常
   │      linkMapper.insert(...)               │ → 整个事务回滚
   │                                          │ → ⑥ 已扣的天自动还回去
   ├─⑧ CancelPolicy.fromCode(1).snapshotJson()┘
   ├─⑨ bookingMapper.insert(booking)   状态=10 待支付
   │
   ▼  返回 Result.ok(bookingId)
```

**注意 ⑥⑦⑧⑨ 全在同一个 `@Transactional` 里** —— 要么全成功，要么全回滚。

### 4.2 最强证据：台账与库存零漂移

       SUM(CASE WHEN l.released=0 THEN l.room_count ELSE 0 END) AS ledger_held,

## 5. P0 过程中发现并修掉的问题

### ① 应用真 bug：`checkAvailability` 对全新日期返回"不可订" 🔴

**现象**：第一次查可订永远返回 `available=false`。

**根因**：库存行是下单时才惰性创建的，而原代码把「没有库存行」当成 `total=0, sold=0 → 剩 0 间`。

**修法**：没有库存行 = 该天还没人订过 → 按 `room_type.total_rooms` 算满房可订。

**为什么值得记**：这个 bug **编译通过、启动通过、日志干净**，只有真正调接口才会暴露。这正说明了第 3 步端到端测试不可省。

### ② 响应缺 charset（兼容性隐患，非 bug）🟡

响应头原来是 `application/json`（**符合 RFC 8259**，JSON 恒为 UTF-8）。但 PowerShell 5.1 这类老客户端会退回 Latin-1 解码 → 中文全变乱码。

我一度误判为"数据库中文乱码"，查了原始字节才确认：

```
DB 里的字节: E5858DE8B4B9E58F96E6B688 = 免费取消   ← 本来就是对的
显式按 UTF-8 解码响应 → 杭州西湖畔精选酒店 / 高级大床房 / 已取消 / 免费取消   全部正确
```

**修法**：`application.yaml` 加 `server.servlet.encoding.force: true` → 响应头变为 `application/json;charset=UTF-8`。

### ③ 我自己测试脚本的 bug 🟡

脚本里**错误分支**用 `StreamReader(..., UTF8)` 显式解码，**成功分支**用 `$r.Content`（PS 默认解码）。结果报错信息中文正常、成功响应中文乱码 —— 正是这个不一致把我带偏了。

**修法**：统一改成从原始字节显式按 UTF-8 解码（[p0_flow_test.ps1](F:\JavaProject\devops\p0_flow_test.ps1)）。

**P1 要特别想清楚的一件事**：

> Redis 预占成功了，但 DB 那边失败（比如某天不够）时，怎么保证 Redis 的预占被清理干净？

这正是 TaxiAgent 里那条原则的用武之地 —— **「Redis 只做加速，DB 才是裁决者」**。所以 P1 的设计必须是：

```
Redis 预检预占（快，扛并发）
      ↓ 通过
DB 逐天条件 UPDATE（准，最终裁决）
      ↓ 失败
抛异常 → 事务回滚 DB + 【补偿清理 Redis】
```

而且 **Lua 里必须先全查、再全扣**（两趟），不能边查边扣 —— 否则第 3 天不够时前 2 天已经扣了，在 Lua 里做补偿很别扭。
