## 2. 核心机制详解

### 2.1 左闭右开（`BookingServiceImpl:673` / `:690`）

```java
private void validateRange(LocalDate checkIn, LocalDate checkOut) {
    if (!checkIn.isBefore(checkOut)) throw BusinessException.badRequest("离店日期必须晚于入住日期（区间左闭右开）");
    ...
}

/** 展开入住区间 [checkIn, checkOut) 的每一天 */
private List<LocalDate> stayDates(LocalDate checkIn, LocalDate checkOut) {
    List<LocalDate> dates = new ArrayList<>();
    for (LocalDate d = checkIn; d.isBefore(checkOut); d = d.plusDays(1)) {   // ← isBefore，不是 !isAfter
        dates.add(d);
    }
    return dates;
}
```

**全项目只有这两处实现区间语义** —— 下单、算价、扣库存、释放、改期、超时，全都调用它们。这样就不可能"某处多算一天"。

验证证据：订 `10/12→10/15`，台账里只有 **10/12、10/13、10/14** 三行。

### 2.2 逐天条件 UPDATE（`RoomInventoryMapper:42`）

```sql
UPDATE room_inventory SET sold_rooms = sold_rooms + #{n}, version = version + 1
WHERE room_type_id = #{roomTypeId} AND stay_date = #{stayDate}
  AND sold_rooms + #{n} <= total_rooms        -- ★ 条件写在 WHERE 里
```

**"够不够"和"扣减"在同一条语句里完成**，靠数据库行锁保证原子性。调用方只看影响行数：

```java
int updated = roomInventoryMapper.tryOccupy(dto.getRoomTypeId(), d, roomCount);
if (updated == 0) {
    throw BusinessException.conflict(d + " 房量不足，请调整日期或间数");
}
```

> **这就是"条件的判定与执行不可分离"** —— 如果先 `SELECT` 判断再 `UPDATE`，两步之间就有窗口期，两个并发请求会同时通过判断，造成超卖。把条件塞进 `WHERE` 就不存在这个窗口。

### 2.3 为什么不需要手写补偿（`createBooking:191`）

```java
@Transactional(rollbackFor = Exception.class)     // ← 关键在这一行
public Long createBooking(CreateBookingDTO dto) {
    ...
    for (LocalDate d : dates) {
        roomInventoryMapper.insertIgnore(...);
        int updated = roomInventoryMapper.tryOccupy(...);
        if (updated == 0) {
            throw BusinessException.conflict(...);   // 抛异常 = 让整个事务回滚
        }
    }
}
```

住 5 晚就要扣 5 天，第 4 天不够时**前 3 天已经扣掉了**。这里**没有任何"把前 3 天加回去"的补偿代码** —— `@Transactional` 让整个事务回滚，前 3 天的 UPDATE 自然被撤销。

验证证据（超卖测试）：订 3 间成功后抢第 4 间失败，库存**仍精确是 2 天 × 3 间 = 6**，无半占残留。

> **对比 TaxiAgent**：它抢的是"单个司机"，失败只需把一个值设回哨兵；这里是"占 N 天"，手写补偿极容易漏一天。

### 2.4 ★ 台账（`booking_inventory_link`）—— 本项目的骨架

**一句话：订单是"意图"，台账是"已发生的事实"。**

```
booking（1 行）                    booking_inventory_link（N 行）
────────────────────────           ──────────────────────────────────────────
booking_id  = B123                 B123 | 2001 | 2026-10-12 | 1 间 | released=0
check_in    = 2026-10-12           B123 | 2001 | 2026-10-13 | 1 间 | released=0
check_out   = 2026-10-15           B123 | 2001 | 2026-10-14 | 1 间 | released=0
room_count  = 1
        ↑ 这份会被改                    ↑ 这份按 (订单,日期) 复用，已释放的行保留为历史
```

**它解决的四个问题**：

| 场景 | 没有台账会怎样 |
|---|---|
| **改期** | 更新订单的 `check_in/check_out` 会**覆盖掉"原来占了哪几天"**，旧日期的库存**永久找不回来**（静默丢房，且不报错） |
| **部分取消** | 只能整单取消，做不到"取消后 2 晚" |
| **对账** | 要回答"10/20 被哪些订单占了"，得扫**所有**订单做区间重叠判断（正是 §2 里说"性能极差"的那条路） |
| **释放幂等** | `released` 标记**必须落在"某一天"的粒度**上；放在订单上就拦不住交叉释放 |

**★ 台账行是复用的，不是每次新增的**：

```
初始              11/09、11/10、11/11                      3 行 released=0
改到 11/16-11/18  11/09、10、11 → released=1（保留）
                  11/16、11/17 → 新增                       5 行（2 行 held）
改回 11/09-11/12  11/16、11/17 → released=1（保留）
                  11/09、10、11 → upsert 翻回 released=0    5 行（3 行 held）
```

所以记住：

```
台账行数 ≠ 当前占用天数
"当前占着几天" = WHERE released = 0 的行数
```

**更深一层：台账才是库存的事实来源。**

```
room_inventory.sold_rooms        ←  汇总出来的计数器（可重建）
booking_inventory_link           ←  原始台账（事实）
```

`room_inventory.sold_rooms` 完全可以从台账重算：

```sql
SELECT room_type_id, stay_date, SUM(room_count)
FROM booking_inventory_link WHERE released = 0
GROUP BY room_type_id, stay_date;
```

如果 `sold_rooms` 被搞坏（手动改库 / 程序 bug），就按这个重建。**这跟"Redis 只做加速、DB 才是裁决者"是同一套思路 —— 只是 DB 内部也分了「明细」和「汇总」两层。** 到 P1 会有第三份副本（Redis 预占），三份里只有台账能反过来重建另外两份。

### 2.5 台账释放：先标记，再还库存（`releaseInventory:528`）

```java
List<BookingInventoryLink> links = linkMapper.selectUnreleased(bookingId);
for (BookingInventoryLink link : links) {
    int marked = linkMapper.markReleased(link.getId());   // ★ 带 released=0 前置条件
    if (marked == 0) {
        continue;                                          // 已被别的流程释放过，跳过
    }
    int released = roomInventoryMapper.release(...);       // 只有抢到标记的人才能还库存
    if (released == 0) {
        log.error("库存释放异常（台账与库存不一致）: ...", ...);
    }
}
```

```sql
UPDATE booking_inventory_link SET released = 1, release_time = NOW()
WHERE id = #{id} AND released = 0        -- ★ 抢占式
```

**顺序不能颠倒**。先还库存再标记的话，两个并发流程会各还一次 → 库存被加回去两遍 → 凭空多出房间。

这与 TaxiAgent 的**「一次性令牌」**同一个思路：**让数据库决定"谁抢到了这一次操作"**，而不是靠应用层判断。

### 2.6 状态流转也是条件 UPDATE（`BookingMapper`）

```sql
-- markPaid: 10 -> 20
UPDATE booking SET booking_status = 20, paid_amount = ?, pay_time = NOW(), update_time = NOW()
WHERE booking_id = ? AND booking_status = 10 AND is_deleted = 0
```

```java
int updated = bookingMapper.markPaid(bookingId, b.getTotalAmount());
if (updated == 0) {
    throw BusinessException.conflict("订单状态已变化，请刷新后重试");
}
```

**读到的状态不作准，UPDATE 打中几行才算准。**

> 注意 SQL 里显式写了 `is_deleted = 0`。MyBatis-Plus 的 `@TableLogic` **只对它自己生成的 SQL 生效**，手写 `@Update` 必须自己带上。

### 2.7 取消政策快照（`parseSnapshot:556`）

下单时把当时的规则**冻结**进订单：

```json
{"policy":1,"name":"免费取消","tiers":[{"minHoursBefore":0,"refundRatio":"1.000"}]}
```

退款时**读快照，不读当前枚举** —— 否则改一次政策、发一次版，**所有历史订单都会被追溯适用新规则**，用户会投诉"我下单时不是这么说的"。

> **硬编码枚举 ≠ 可以不做快照**，这是两件独立的事。

**退款的兜底规则（§5④ 修掉的那个 bug）**：`hoursUntilCheckIn` 以**入住日 00:00** 为基准，入住当天取消会算出**负数**。此时要**回落到最后一档**，而不是返回 0 —— 否则"任意时间全退"的政策会变成一分不退。

验证：RT2002（限时免费）距入住 32 小时取消 → 命中 `>=24h` 档 → 退 50%（1000 → 500）。

### 2.8 ★ 改期：只动差集（`rescheduleBooking:369`）

**核心**：把旧日期集合和新日期集合做差，**只动差集，重叠部分一根手指都不碰**。

```java
Set<LocalDate> oldSet = new LinkedHashSet<>(oldDays);
Set<LocalDate> newSet = new LinkedHashSet<>(newDays);

List<LocalDate> toRelease = oldDays.stream().filter(d -> !newSet.contains(d)).toList();
List<LocalDate> toOccupy  = newDays.stream().filter(d -> !oldSet.contains(d)).toList();
List<LocalDate> untouched = newDays.stream().filter(oldSet::contains).toList();
```

**为什么不能"先全释放、再全占用"**：

```
把 10/12~10/15 改成 10/13~10/16
  先全释放 → 10/12、10/13、10/14 全部放开
  再全占用 → 10/13、10/14、10/15
                ↑ 10/13、10/14 在中间那一刻被放开过
```

万一那一瞬间被别人抢走，**用户自己"续住"反而失败**，而这两天本来一直是他占着的。

只有台账能告诉我们"他到底占着哪几天"，从而算出真正的差集。

**实测证据（案例 B：`10/20-10/23` → `10/21-10/24`）**：

```
released  = [10/20]              只有 1 天释放
occupied  = [10/23]              只有 1 天占用
untouched = [10/21, 10/22]       2 天一动没动

10/21 的 version = 1  （改期前后都是 1）
10/22 的 version = 1
```

**`version` 不增长，就是"真的一下都没碰"的硬证据** —— 若走"全释放再全占用"，这两天的 version 会各 +2。

**失败要能整体回滚**：改期也是先释放、后占用，两次操作都在同一事务里。如果占用某天时发现满房，抛异常 → 已释放的天被还回来、已占用的天被撤销、订单日期不变。

实测（`11/23-11/26` 改到 `11/29-12/02`，其中 `11/30` 满房）：

```
HTTP 409 "2026-11-30 房量不足，改期失败"
11/23、11/24、11/25  仍然 held     ← 已释放的被还回来了
11/29                NOT held      ← 已占用的被撤销了
订单日期没变
```

**一个坑：`UNIQUE(booking_id, stay_date)` 与"改回来"**

同一个订单可能改回原日期（`10/12→10/15` 改到 `10/20→10/22` 再改回来）。那时旧台账行还在（`released=1`），直接 `insert` 会撞唯一键。所以用 upsert 把 `released` 翻回 0：

```sql
INSERT INTO booking_inventory_link (...) VALUES (...) AS new
ON DUPLICATE KEY UPDATE released = 0, release_time = NULL, room_count = new.room_count
```

这是安全的：那几天的库存"先减后加"，净效果为零，不会重复计数。

### 2.9 惰性建库存行（`RoomInventoryMapper:28`）

```sql
INSERT IGNORE INTO room_inventory (room_type_id, stay_date, total_rooms, sold_rooms, version)
VALUES (?, ?, ?, 0, 0)
```

库存日历**不预先铺满**，用到哪天建哪天，靠 `UNIQUE(room_type_id, stay_date)` 保证并发下只成功一次。

配套要点：`checkAvailability` 遇到**没有库存行**时，按 `room_type.total_rooms` 当成"满房可订"，而不是当成 0 间 —— 这正是 §5① 修掉的那个 bug。

> 生产环境的做法通常是**定时任务提前物化未来 N 天的库存**（酒店的"房态"）。P0 先用惰性建行，P2 的定时任务会补上。

## 3. 一次下单的完整调用链

```
POST /booking  {"userId":9001,"hotelId":1001,"roomTypeId":2001,
                "checkIn":"2026-10-12","checkOut":"2026-10-15","roomCount":1}
   │
   ▼  BookingController.create()                            :42
   │     @Valid 校验请求体
   ▼  BookingServiceImpl.createBooking()   @Transactional   :191
   │
   ├─① validateRange(10/12, 10/15)                           :673   区间合法？
   ├─② requireRoomType(2001)                                 :653   房型存在且在售？
   ├─③ hotelMapper.selectOne(...)                                  酒店存在？
   ├─④ quotePrice(...)                                       :144   算钱，缺价格日历就在这拦下
   │      roomPriceMapper.selectRange(2001, 10/12, 10/15)  → 3 × 400 = 1200
   ├─⑤ IdWorker.getId()  → bookingId（雪花）
   │
   ├─⑥ for (d : [10/12, 10/13, 10/14])        ★ 逐天占库存
   │      roomInventoryMapper.insertIgnore(2001, d, 3)
   │      updated = roomInventoryMapper.tryOccupy(2001, d, 1)
   │      if (updated == 0) throw 409 ────────┐
   │                                          │ 任何一天失败
   ├─⑦ for (d : 同上)  写 3 行台账             │ → 抛异常
   │      linkMapper.insert(...)               │ → 整个事务回滚
   │                                          │ → ⑥ 已扣的天自动还回去
   ├─⑧ CancelPolicy.fromCode(1).snapshotJson()┘
   ├─⑨ bookingMapper.insert(booking)   状态=10 待支付
   │
   ▼  返回 Result.ok(bookingId)
```

**⑥⑦⑧⑨ 全在同一个 `@Transactional` 里** —— 要么全成功，要么全回滚。

| **B 平移重叠** `10/20-10/23→10/21-10/24` | **10/20** | **10/23** | **10/21,10/22** | 0 |
| C 缩短 `11/02-11/05→11/02-11/03` | 11/03,11/04 | — | 11/02 | **−800** |
| D 错开 `11/09-11/12→11/16-11/18` | 11/09,10,11 | 11/16,11/17 | — | −400 |
| D' **再改回** `11/16-11/18→11/09-11/12` | 11/16,11/17 | 11/09,10,11 | — | +400 |
| E 失败回滚（11/30 满房） | — | — | — | **409 且全部还原** |
| F 状态校验 | 已取消 → 409；日期相同 → 400 | | | |

**关键断言**：A 的 `10/12`、B 的 `10/21` 和 `10/22`，**`version` 改期前后完全相同** —— 未受影响日期确实一下都没碰。

### 4.3 最强证据：台账与库存零漂移

```sql
SELECT COUNT(*) FROM room_inventory i
LEFT JOIN (SELECT room_type_id, stay_date, SUM(room_count) n
           FROM booking_inventory_link WHERE released = 0
           GROUP BY room_type_id, stay_date) l
  ON l.room_type_id = i.room_type_id AND l.stay_date = i.stay_date
WHERE i.sold_rooms <> IFNULL(l.n, 0);
-- => 0
```

走完 **下单 / 支付 / 取消 / 重复取消 / 超卖失败 / 超时失效 / 改期（5 种形态）/ 改期失败回滚** 全部路径后，**台账与库存逐行相等**。

## 5. 过程中修掉的问题

### 应用真 bug

**① `checkAvailability` 对全新日期返回"不可订"** 🔴

库存行是下单时才惰性创建的，原代码把「没有库存行」当成 `total=0 → 剩 0 间`。**第一次查可订永远返回 false。**

修法：没有库存行 = 该天还没人订过 → 按 `room_type.total_rooms` 算满房可订。

> 这个 bug **编译通过、启动通过、日志干净**，只有真正调接口才暴露。

**④ 入住当天取消，「免费取消」退 0** 🔴

`hoursUntilCheckIn` 以入住日 00:00 为基准，入住当天取消算出**负数**；`refundRatio` 在"低于所有档位"时**直接返回 0** —— 连"任意时间全退"也一分不退。

修法：没命中任何档位时**回落到最后一档**。现场验证：`refund=1200.00 ratio=100%`（修前是 0）。

**② 响应缺 charset（兼容性隐患）** 🟡

响应头原是 `application/json`（符合 RFC 8259，JSON 恒为 UTF-8），但 PowerShell 5.1 这类老客户端会退回 Latin-1 解码 → 中文全乱码。已加 `server.servlet.encoding.force: true`，响应头变为 `application/json;charset=UTF-8`。

### 工具 / 测试的 bug（更值得记，因为症状会骗人）

**⑤ 我写的隧道脚本：socket 重绑导致"端口在监听却连不上"** 🔴

重连时代码是 `s.shutdown()` + 重新 `bind`。但 `shutdown()` **只停 `serve_forever` 循环，不关闭监听 socket**（要 `server_close()`）；而 `allow_reuse_address=True` 让 Windows 允许同一端口重复绑定 → **同一端口上两个 socket 并存**，新连接可能落到持有**已死 transport** 的旧 server 上。

症状极具迷惑性：**端口 LISTENING，一连上就被关**，应用和 SQL 客户端全部失败，而日志里写着"重连完成，隧道恢复"。

修法：**重连时只替换 transport 引用，根本不重建 socket**（监听 socket 本来就跟 SSH 连接无关）。

**③ 测试脚本的错误分支和成功分支解码方式不一致** 🟡

错误分支用 `StreamReader(..., UTF8)` 显式解码、成功分支用 `$r.Content`（PS 默认解码）→ 报错信息中文正常、成功响应中文乱码。这个不一致把我一度带偏成"数据库中文乱码"。

修法：统一从原始字节显式按 UTF-8 解码。

**⑥ 测试断言把台账历史行数搞错** 🟡

我以为改回来后台账还是 3 行，实际是 5 行（3 行 re-held + 2 行历史）。见 §2.4 —— **台账是流水，保留历史，不是投影**。

### 附带发现：PowerShell 5.1 的行数统计不可靠

```
LF(\n) 计数 = 713    ReadAllLines().Length = 713    ← 一致，可信
(Get-Content).Count = 688                            ← 少 25 行
Measure-Object -Line = 609                           ← 少 104 行（不数空行）
```

全项目用 `ReadAllLines` 求和 = **3470**，与 git 报告的 insertions **完全吻合**。以后统计行数一律用 `[IO.File]::ReadAllLines()`。

## 8. 通往 P1：要动哪些地方

P1 = **区间库存 Lua + 回滚补偿 + 接口幂等**。改动点很集中：

| 位置 | 现在 | P1 之后 |
|---|---|---|
| `pom.xml` | 无 Redis 依赖 | 加 `redisson-spring-boot-starter` |
| `application.yaml` | 无 redis 配置 | 加 `spring.data.redis`（隧道 16379） |
| 新增 `RedisKeyConstants` | — | 集中管理 key 名，避免散落 |
| 新增 `RedisScripts` | — | 存 Lua 脚本（**区间预检预占**是核心） |
| `createBooking:191` 的 ⑥ 段 | 直接逐天 `tryOccupy` | 前面插一段 Redis Lua 预检预占；DB 那段**保留**作为最终裁决 |
| `releaseInventory:528` / `releaseOneDay:452` | 只还 DB | 多一步：同步回滚 Redis 预占 |
| 新增 `@Idempotent` + AOP | — | 幂等注解，底层 `SET NX EX` + `idempotent_record` 落库兜底 |
| `db/schema.sql` | 8 张表 | 追加 `idempotent_record` |

**P1 要特别想清楚的一件事**：

> Redis 预占成功了，但 DB 那边失败（某天不够）时，怎么保证 Redis 的预占被清理干净？

这正是 TaxiAgent 那条原则的用武之地 —— **「Redis 只做加速，DB 才是裁决者」**：

```
Redis 预检预占（快，扛并发）
      ↓ 通过
DB 逐天条件 UPDATE（准，最终裁决）
      ↓ 失败
抛异常 → 事务回滚 DB + 【补偿清理 Redis】
```

而且 **Lua 里必须先全查、再全扣**（两趟），不能边查边扣 —— 否则第 3 天不够时前 2 天已经扣了，在 Lua 里做补偿很别扭。

**另一个提醒**：P0 已经把"台账是事实来源"验证得很扎实。P1 引入 Redis 后会有**三份数据**（Redis 预占、`room_inventory.sold_rooms`、台账），对账工具仍然是 §4.3 那条一致性 SQL —— 建议 P1 直接把它固化成测试用例。
