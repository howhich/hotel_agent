## 1. ★ 三层库存数据

P1 之后，"某天还剩几间房"这个事实有**三份**记录。搞不清它们的关系就会写出错代码，所以先讲这个。

```
① Redis 预占            hotel:inv:{rt:2001}:2026-11   →  hash: { 2026-11-02: 1 }
② room_inventory        sold_rooms（一行一天）
③ booking_inventory_link  台账（一行 = 某单在某天占了几间）
```

### 1.1 角色分工

| 层 | 角色 | 能不能被重建 | 丢了会怎样 |
|---|---|---|---|
| ① Redis | **加速**：把"明显不够"的请求在进 DB 之前拒掉 | 能 —— 从 ② 回源 | 一次 cache miss，退化成纯 DB 路径；**不影响正确性** |
| ② `sold_rooms` | **汇总计数器**：并发扣减的落点（`UPDATE ... WHERE sold_rooms + n <= total`） | 能 —— 从 ③ 重算 | 需要人工重建 |
| ③ 台账 | **事实来源**：谁在什么时候占了哪天、占了几间 | ❌ **不能** | 库存彻底失去依据 |

### 1.2 谁能重算谁

```sql
-- 从台账重算 sold_rooms（②）
SELECT room_type_id, stay_date, SUM(room_count)
FROM booking_inventory_link WHERE released = 0
GROUP BY room_type_id, stay_date;
```

```
③ 台账  ──可重算──>  ② sold_rooms  ──可回源──>  ① Redis
```

**只有箭头朝外，没有朝里。** 所以：`sold_rooms` 不是权威数据，它是"为了并发扣减而做的加速计数器"；Redis 更不是。

> 这跟"Redis 只做加速、DB 才是裁决者"是同一个思路，只是 **DB 内部也分了「明细」和「汇总」两层**。

### 1.3 三份数据什么时候会不一致

| 场景 | 后果 | 处理 |
|---|---|---|
| Redis 键 **TTL 到期**（24h） | 缓存空 | 下次用到自动回源，**无害** |
| Redis 被 **`allkeys-lru` 淘汰** | 缓存空 | 同上，**无害** |
| 下单时 **Redis 放行、DB 拒绝** | Redis 多占了几间（假如不补偿） | **事务回滚回调里补偿**（见 §2） |
| Redis 里的值和 DB **真的不一样**（漂移） | 缓存过滤能力下降（但 DB 仍兜底） | `GET /booking/inv/compare` 检出 → `POST /booking/inv/rebuild` 修复 |
| `sold_rooms` 被人工改坏 | 可能超卖 | 从台账重算 |

> **服务器上 Redis 配的是 `allkeys-lru`**（会淘汰任何键，包括没设 TTL 的）。对本项目**无害**，因为这里放的全是可从 DB 重建的派生数据。
>
> 这与 TaxiAgent 的情况不同 —— 它把"延迟队列""司机在线状态"这类**唯一事实来源**也放在 Redis 且不设 TTL，被淘汰就是丢数据。

### 1.4 对账的语义（容易写错）

`compareWithDb()` 判断"漂移"的规则是：

```
漂移     = ① 和 ② 都有值，且不一样
没缓存   = ① 里没有这一天 → 【不算漂移】
```

**为什么"没缓存"不算漂移**：缓存是懒加载的，没被预订过的日期本来就不会有值；真要用到时会回源 DB，取到的就是 DB 的值。

我第一版把它算成漂移了，结果测出一个 `10/31→11/02` 的订单时报了 36 条"差异" —— 因为 11/02 是**离店日**，从没被占用过，缓存里当然没有它。

## 2. ★ 双写时序

这是 P1 最核心的设计。**Redis 和 DB 是两份数据，动它们的顺序不能随便定。**

### 2.1 规则表

| 操作 | Redis 何时动 | DB 何时动 | 事务回滚时 |
|---|---|---|---|
| **下单**（占用） | 预检预占，**在最前面** | 逐天条件 UPDATE | **补偿：把预占还回去** |
| **改期**（新占的天） | 预检预占，**在最前面** | 逐天条件 UPDATE | **补偿：把预占还回去** |
| **取消 / 失效** | 释放，**在事务提交之后** | 逐天还原 | 什么都不做 |
| **改期**（释放的天） | 释放，**在事务提交之后** | 逐天还原 | 什么都不做 |

一句话：

> **占用型先动缓存（为了快），释放型后动缓存（为了准）。**

- **占用型**：Redis 存在的全部意义就是"在碰 DB 之前就拒掉"。所以它必须在最前面 —— 代价是可能留下幽灵预占，**必须补偿**。
- **释放型**：先释放缓存毫无好处（缓存提前说"有房"，别人冲进来还是会被 DB 拒），反而在事务回滚时会留下漂移。所以**等 DB 提交成功再动**。

### 2.2 为什么补偿放在 `afterCompletion` 而不是 `try/catch`

```java
// 错的做法：只能覆盖"方法体抛异常"
try {
    ... DB 操作 ...
    return bookingId;
} catch (RuntimeException e) {
    cache.releaseAll(...);      // ← 漏了一种情况
    throw e;
}
```

`try/catch` 覆盖不到 **"提交阶段才失败"** —— 比如 commit 时检测到死锁、或者连接在 commit 途中断掉。那时候方法体早就正常返回了，`catch` 根本不会执行，但事务**确实回滚了** → Redis 预占**永远留在那里**（凭空少几间房，且没有任何报错）。

正确做法（[BookingServiceImpl:625](../src/main/java/com/fancy/hotel/service/impl/BookingServiceImpl.java#L625)）：

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCompletion(int status) {
        if (status == STATUS_COMMITTED) { onCommit.run(); }
        else                            { onRollback.run(); }
    }
});
```

`afterCompletion` 在事务**真正结束之后**才回调，两种情况都能兜住。

### 2.3 两处调用点的参数正好相反

```
createBooking    → afterTransaction(null, () -> cache.releaseAll(...))   回滚才动缓存
releaseInventory → afterTransaction(() -> cache.releaseOne(...), null)   提交才动缓存
```

### 2.4 一个故意留的坑

改期的 `releaseOneDay()`（[:501](../src/main/java/com/fancy/hotel/service/impl/BookingServiceImpl.java#L501)）**只动 DB，不碰 Redis**。

改期要释放的那几天，Redis 的释放统一放在那个 after-commit 回调里（[:459](../src/main/java/com/fancy/hotel/service/impl/BookingServiceImpl.java#L459)）。如果顺手在 `releaseOneDay` 里加一句 `releaseOne`，就会**双重释放**：Redis 被减两次 → 缓存凭空多出房间 → 快路径过滤能力下降。

代码里留了注释提醒。

## 3. ★ 接口幂等

### 3.1 解决什么问题

用户在支付页手抖点两下 = 下两张单 = 占两次库存。

TaxiAgent 的文档里明确把这条列为未实现："接口幂等（通用机制）：无幂等注解/切面"。P1 补上它。

### 3.2 幂等键

```
幂等键 = 业务类型 + 参数指纹

参数指纹（二选一，优先客户端）：
  ① 请求头 Idempotency-Key  ← 客户端重试时最可靠
  ② 方法参数的 SHA-256       ← 没传头时，同一份请求体算同一个请求
```

实际落库的键长这样（从测试里抓的真实数据）：

```
hotel:idem:CREATE_BOOKING:h:client-key-DEMO-001
hotel:idem:CREATE_BOOKING:f:93da2272d091f1fa53c501...
```

`h:` = header，`f:` = fingerprint，一眼能看出是哪条路来的。

### 3.3 两层防御 + 结果回放

[IdempotentAspect:70](../src/main/java/com/fancy/hotel/config/IdempotentAspect.java#L70)

```
Redis SET NX  ──失败──> 回放首次结果（或"请求正在处理中"）
     │成功
DB 插唯一键   ──撞键──> 回放首次结果（第一层没兜住时）
     │成功
执行业务      ──抛异常──> 删记录 + 删 Redis 键（让用户能重试）→ 原样抛出
     │成功
记录结果（DB.result_ref + Redis "DONE:<ref>"）→ 返回
```

| 层 | 手段 | 作用 |
|---|---|---|
| 第一层 | Redis `SET idem_key RUNNING NX EX 600` | 快，扛并发 |
| 第二层 | `idempotent_record.uk_idem_key` | Redis 挂了 / 跨实例时兜底；顺便存 `result_ref` 做回放 |

**回放**：重复请求返回**首次的 `booking_id`**，而不是报错；同时打 `X-Idempotent-Replay: true` 头方便区分。

### 3.4 三个关键细节

**① 切面必须早于 `@Transactional`**

```java
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
```

否则"插入幂等记录"会跟着业务事务一起回滚，**第二层防御直接失效**。

**② 失败要删记录，不能标记失败**

业务方法都是 `@Transactional`，失败 = 没有副作用。保留一条"失败记录"只会让用户的重试也被拒。

测试里验证了：占满库存后连发两次同样的请求，两次得到的都是 **"房量不足"**，不是 **"请勿重复提交"**。

**③ fail-open**

幂等键构造失败、或 Redis 不可用时**放行**。不能因为幂等机制自身的问题挡住正常业务。

**④ 只支持有限返回类型的回放**

[convertRef:179](../src/main/java/com/fancy/hotel/config/IdempotentAspect.java#L179) 支持 `Long` / `Integer` / `String` / `void`，其它类型直接抛异常 —— 不做"看起来能用其实不对"的静默降级。

### 3.5 一个容易被忽略的点：幂等状态也是测试状态

`idempotent_record` 和 `hotel:idem:*` 是**只增不减、跨请求存在**的状态。测试的 `ResetTestData` 一开始只清了 booking / inventory / ledger，结果：

```
连跑套件 → P0 测试下单 → 命中上一轮幂等测试留下的记录
                       → 回放了一个早已被取消的旧 bookingId
                       → 9 个断言集体失败，看起来像功能坏了
```

现在 `ResetTestData` 会一起清掉它们（见 [test/README.md](../test/README.md)）。

## 4. Redis 数据结构与 Cluster 考量

### 4.1 为什么是"房型 + 月"的 hash

```
key   hotel:inv:{rt:2001}:2026-11     (Hash)
field 2026-11-02
value 已售间数
```

- **不是"一个房型一个 hash"**：那样一年 365 个 field 会无限增长，而且没法按时间段淘汰
- **按月分桶**：bucket 有自然边界，能整体过期

### 4.2 `{rt:2001}` 是 hash tag，不是格式

花括号里的是 Redis Cluster 的 **hash tag**：集群只对 tag 做槽位计算，所以**同一房型的所有月份落同一个 slot**。

这样"跨月的日期区间"（比如 10/31→11/02）才能在**一次 Lua 调用**里操作多个 key —— 集群模式下 Lua 不允许跨 slot 访问。

单机模式下这个 tag 没有副作用，所以 P1 现在用着也不亏。

## 5. Lua 为什么必须两趟

[inventory_reserve.lua](../src/main/resources/lua/inventory_reserve.lua)

```lua
-- 第一趟：全查
while i <= #ARGV do
  local sold = redis.call('HGET', k, d)
  if sold == false then return {'MISS', d} end
  if tonumber(sold) + n > total then return {'REJECT', d} end
  i = i + 2
end

-- 第二趟：全扣（能走到这里说明每天都够）
while i <= #ARGV do
  redis.call('HINCRBY', KEYS[ki], d, n)
  i = i + 2
end
```

**边查边扣会怎样**：住 5 晚，第 4 天不够 → 前 3 天**已经 `HINCRBY` 扣掉了**。此时要在 Lua 里把它们加回去，而 **Redis 的 Lua 没有事务语义**：脚本中间报错，前面的写已经生效，不会自动回滚。

两趟就把这个问题彻底消掉：**第一趟保证"都够"，第二趟才写。**

### 5.1 脚本的返回值全是字符串

```
{'OK'}                全部成功
{'MISS',   date}      该天不在缓存 → 调用方回源后重试
{'REJECT', date}      该天剩余不足
{'BADREQ', reason}    参数不合法
```

**不放数字进返回值**：`StringRedisTemplate` 的结果反序列化用字符串序列化器，混进整数容易在类型转换上出问题。

## 6. 缓存不可用时的降级路径

`tryReserve()` 返回三态，**`CACHE_MISS` 不是失败**：

[:129](../src/main/java/com/fancy/hotel/service/InventoryCacheService.java#L129)

```java
case "OK":     return ReserveResult.ok();        // 已预占，继续走 DB
case "REJECT": return ReserveResult.rejected(d); // 缓存说不够 → 直接 409，不碰 DB
case "MISS":   loadRangeFromDb(...); break;      // 回源后重试一次
```

调用方（[createBooking:217](../src/main/java/com/fancy/hotel/service/impl/BookingServiceImpl.java#L217)）只在 `OK` 时注册补偿，`CACHE_MISS` 时**什么都不做** —— 就退化成 P0 的纯 DB 路径。

> **绝不能因为缓存的问题让用户下不了单。**

### 6.1 回源 vs 重建：两个不同的 Redis 命令

| 方法 | 命令 | 语义 |
|---|---|---|
| `loadRangeFromDb` [:250](../src/main/java/com/fancy/hotel/service/InventoryCacheService.java#L250) | **HSETNX** | 只补缺失的，**绝不覆盖** —— 回源不能冲掉并发预占 |
| `rebuildRangeFromDb` [:273](../src/main/java/com/fancy/hotel/service/InventoryCacheService.java#L273) | HSET | **覆盖写** —— 运维修复，故意要盖掉 |

回源如果用 HSET 就危险了：两个请求同时发现缓存缺失、都去回源，后来的那个会把先到的预占**冲掉**。

### 8.2 P1 的三个决定性证据

**① Redis 快路径真的在拦请求**

让 Redis 说"满"、DB 说"空"，然后下单：

```
Redis 2026-11-23 = 3   DB 2026-11-23 = 0
下单 → 409「2026-11-23 房量不足」
     → DB 的 sold 仍是 0        ← DB 根本没被碰过
     → booking 表没有新行        ← 没建单
```

**推理**：如果 Redis 没拦，请求会走到 DB，而 DB 是 `0+1 <= 3` —— **它会痛快放行并建单**。所以"没建单"就直接证明了拦截发生在 Redis 层。

**② 事务回滚时 Redis 预占真的被补偿**

让 Redis 比 DB 旧：

```
DB 3/3（满）   Redis 0/0（故意弄旧）
下单 → Redis 放行 → DB 拒绝 → 409 → 事务回滚 → 补偿
结果: Redis 回到 0/0     ← 不是 1/1
```

`1/1` 就是补偿失败的样子。

**③ 幂等在 Redis 被清空后仍能工作**

```
Redis 幂等键清掉 3 个，DB 记录还在
重放同一请求 → 200，回放同一个 bookingId，replay=true
```

证明**第二层（DB 唯一键）不是摆设**。

### 8.3 一致性检查（每次跑测试都做）

```sql
-- 台账 vs 库存
SELECT COUNT(*) FROM room_inventory i
LEFT JOIN (SELECT room_type_id, stay_date, SUM(room_count) n
           FROM booking_inventory_link WHERE released = 0
           GROUP BY room_type_id, stay_date) l
  ON l.room_type_id = i.room_type_id AND l.stay_date = i.stay_date
WHERE i.sold_rooms <> IFNULL(l.n, 0);
```

以及 `GET /booking/inv/compare` 确认 Redis 与 DB 零漂移。

## 9. 这一阶段踩过的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | 对账把"没缓存"当成"漂移"，一次报 36 条假差异 | **懒加载的缓存，"没有值"和"值是 0"是两件事** |
| 2 | 幂等切面放错顺序（在 `@Transactional` 里面）会让第二层防御失效 | 切面 `@Order` 要早于事务 |
| 3 | 测试 `ResetTestData` 没清幂等状态 → 套件集体假失败 | **只增不减的跨请求状态，必须纳入重置** |
| 4 | 自写的 SSH 隧道脚本重连时重绑 socket → "端口在监听却连不上" | 见下方 §10 的运维说明 |
| 5 | 测试脚本写死日期，两周后全部失效 | 日期一律相对今天算 |
| 6 | `.ps1` 无 BOM 时 PS 5.1 按 GBK 解码，中文打碎甚至语法错 | 改完必须跑 `test/fix-bom.ps1` |

第 4 条补充：重连时 `s.shutdown()` **只停 `serve_forever` 循环，不关闭监听 socket**（要 `server_close()`），而 `allow_reuse_address=True` 让 Windows 允许同端口重复绑定 → 同一端口上两个 socket 并存，新连接可能落到持有**已死 transport** 的旧 server 上。修法是**重连只替换 transport 引用，不重建 socket**。

## 10. 边界

| 没有 | 说明 | 属于 |
|---|---|---|
| **订单超时的自动释放** | 现在靠手动 `POST /booking/expire-scan`，没有延迟队列 | P2 |
| **附近酒店 GEO / 多维排序** | 只能按 ID 查 | P2 |
| **分布式锁** | 单实例，还没有需要锁的临界区 | P3 |
| **本地缓存（Caffeine）** | 只有 Redis 一层 | P3 |
| **鉴权** | `userId` 仍由请求体传入（**不可上线**） | P4 |
| **幂等的定期清理** | `idempotent_record` 有 `expire_time` 但没有清理任务 | P2/P3 |
| **缓存预热** | 库存缓存是懒加载，没有预热 | 可选 |
| **JUnit 单元测试** | 只有端到端脚本 | 可选 |

## 11. 通往 P2

P2 = **延迟队列（订单超时自动释放）+ 附近酒店 GEO**。

| 位置 | 现在 | P2 之后 |
|---|---|---|
| `expireTimeoutBookings()` | 手动接口 + 扫表 | Redis ZSet 延迟队列，到点精确触发 |
| `expireBooking()` | 已有，逻辑不用改 | 由延迟队列的消费者调用 |
| `hotel` 表 | 有经纬度但从没用过 | `driver:geo` 式 GEO 池 → 酒店 GEO 索引 |
| 新增 | — | `RedisKeyConstants` 加延迟队列 + GEO 的 key |
| 新增 | — | 幂等记录的清理任务（扫 `expire_time`） |

**关键提醒**：延迟队列的 ZSet 是**待办任务**，属于"唯一事实来源"那一类数据 —— 一旦被 `allkeys-lru` 淘汰，任务就丢了（订单永远不会超时释放）。

到时候要么把 Redis 的淘汰策略改成 `volatile-lru`（ZSet 不设 TTL 就受保护），要么把延迟队列落库 + 定时补偿。**这是 P2 第一个要决定的事。**
