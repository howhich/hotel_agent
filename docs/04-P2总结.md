## 0. 这一阶段到底干了什么

P1 做完的时候有个挺尴尬的地方：

> 用户下单了、没付钱，那几间房就一直被占着。因为"超时释放"只有一个**手动接口** —— 谁去调它？没人调，订单就永远不会过期。

P2 解决这个，顺手加了"按位置找酒店"：

| # | 要做的事 | 大白话 |
|---|---|---|
| 1 | 订单到点自动释放 | 下单时贴一张"15 分钟后提醒我"的便签；到点了就把这单作废、把房退回去 |
| 2 | 按位置找附近酒店 | 地图上把每家酒店打个点，问"我周围 3 公里有哪几家"，再按距离 / 评分 / 价格排给你 |
| 3 | 定期清垃圾 | 有些表会越攒越多，有些数据会悄悄残留，得定期扫掉 |

**这一阶段的一句话总结**（后面反复会用到）：

> **快速通道可以丢，账本不能丢。**

意思是：为了快而加的东西（缓存、索引、便签）出问题都还能补救；但真正记录事实的东西（数据库里的订单和台账）绝对不能丢。

新增依赖：**0 个**。

## 1. 订单怎么做到"到点自动释放"

### 1.1 换个说法：便签墙

想象酒店前台有一面墙，上面贴满便签。每张便签写着：

```
处理时间：15:30
内容：   把订单 #888 作废，房退回去
```

**便签墙按处理时间排序**，最上面那张就是"最早该处理的"。墙上还有一个闹钟每分钟响一次：响的时候看看第一张便签的时间到了没，到了就撕下来、照着做。

这就是延迟队列的全部。

技术上，这面墙是 Redis 里的一个 **ZSet**（有序集合）—— 你可以理解成"会自动按分数排序的名单"：

```
key    hotel:delay:order        名单的名字
score  触发时刻（毫秒时间戳）    便签上写的处理时间，就是排序依据
member bookingId                便签内容
```

用 ZSet 而不是普通列表，是因为它天生就按 score 排好序了 —— 问"现在有哪些该处理了"也就是一条命令的事。

### 1.2 ★ 便签丢了会怎样？这才是重点

这里有个特别容易被忽略的区别：

| | 库存缓存（P1 那个） | 延迟队列（P2 这个） |
|---|---|---|
| 它是什么 | 从数据库抄出来的**副本** | **待办事情本身** |
| 丢了会怎样 | 下次用的时候重新抄一遍就好 | **订单永远不会被作废，房被永久占着** |
| 会报错吗 | 不会 | **也不会** |

看到问题了吗 —— 第二种情况**不会有任何报错**。房间就那么一直占着，没人发现，直到有客人投诉"怎么订不了房"。

所以服务器上 Redis 的一个配置被改掉了：从 `allkeys-lru` 改成 **`volatile-lru`**。

### 1.3 `volatile-lru` 是什么意思（用大白话讲）

Redis 是内存数据库，内存满了就得**扔掉一些东西**腾地方。扔谁呢？这由"淘汰策略"决定：

| 策略 | 扔哪些 | 后果 |
|---|---|---|
| `allkeys-lru`（原来的） | **所有键里最久没用的** | 便签墙也可能被扔掉 → 待办任务凭空消失 |
| `volatile-lru`（现在的） | **只扔"设了保质期"的键** | 便签墙没设保质期 → 安全；库存缓存设了 24 小时保质期 → 照样能被扔掉 |

```
设了保质期的（库存缓存，24h）  →  内存紧张时可以扔，反正能重建 ✓
没设保质期的（便签墙）        →  永远不扔 ✓
```

一行配置，正好让两类数据各归其位。

### 1.4 但光靠这个还不够：两道保险

即使配置改对了，便签还是可能丢：Redis 重启、被手工清空、下单那一刻恰好没写进去……所以必须再有一道：

```
第一道：便签墙 + 每分钟的闹钟      →  秒级精度，快
第二道：每 5 分钟翻一遍账本        →  慢，但一定能发现"有订单该作废了还没作废"
```

第二道不能省。**它的存在意义就是"便签丢了也能补上"。**

两道同时跑，会不会把同一单处理两遍？不会 —— 因为"作废订单"这个动作本身是安全的：

```sql
UPDATE booking SET booking_status = 91
WHERE booking_id = ? AND booking_status = 10   -- ← 只有还处于"待支付"的才改
```

只有真正改到 1 行的那次才算成功。第二道跑到的时候发现状态已经不是 10 了，直接跳过。

> **这个兜底真的救过一次场。** P2.1 部署完第一次启动，日志里冒出：
> 「兜底扫表释放了 5 个超时订单」——
> 那是 P1 时期留下的待支付订单，当时还没有便签墙，自然没人给它们贴便签。

### 1.5 两张便签亭同时工作，会不会抢到同一张

假设以后开了第二个前台（多实例）。两个闹钟同时响，会不会**都**看到"便签 #888 该处理了"，然后各处理一遍？

单看两条命令的话，会：

```
第一个前台：查一下现在该处理哪些 → 看到 #888
第二个前台：查一下现在该处理哪些 → 也看到 #888   ← 撞车
```

解决办法是把"看一眼"和"撕下来"合成**一个动作**，用 Redis 的 **Lua 脚本**（一段在 Redis 内部连续执行的代码，中间不会被打断）：

```lua
local members = redis.call('ZRANGEBYSCORE', key, '-inf', now, 'LIMIT', 0, limit)
for i = 1, #members do
  if redis.call('ZREM', key, members[i]) == 1 then   -- 谁撕下来，谁负责
    claimed[#claimed + 1] = members[i]
  end
end
```

**能撕下来的那个才去干活**，另一个会发现便签已经不在了。

这跟 P1 里"释放库存"用的是同一个思路：把一个动作变成**一次性令牌**，抢到令牌的才有资格做。

> 现在是单实例，两个人不会真的同时抢。但先把规则写对，不然以后要改的地方就多了。

### 1.6 贴便签的时机：一定要等事情办完

下单的流程是：

```
占库存 → 建订单 → 提交事务  ←── 到这里才算真的成功
贴便签
```

如果先贴便签、再提交事务，事务要是回滚了（比如库存刚好被别人抢走），**便签就留在墙上了** —— 到点闹钟去处理，发现订单根本不存在，白跑一趟。

所以贴便签这一步挂在"事务提交成功后"的回调里。P1 已经有这个机制了（`afterTransaction`），直接用。

支付、取消、作废的时候也要把便签撕掉，免得到点白跑。

## 2. 按位置找酒店

### 2.1 换个说法：地图上打点

给每家酒店在地图上钉一个图钉（经纬度）。客人问"我这儿周围 3 公里有哪些"，就是**以我站的地方为圆心画个圈，看圈里有几个图钉**，再按远近排给你。

技术上用的是 Redis 的 **GEO**（地理索引）功能：

```
GEOADD    hotel:geo:all <经度> <纬度> <酒店ID>        ← 钉图钉
GEOSEARCH hotel:geo:all FROMLONLAT <经度> <纬度> BYRADIUS 3 km ASC WITHDIST  ← 画圈
```

最后一个参数 `WITHDIST` 表示"顺便告诉我每个点离我多远"。

### 2.2 它跟库存缓存是同一种东西

这个地图索引是**从数据库里的酒店表抄出来的**，随时可以扔掉重建：

```
数据库的 hotel 表  →  （可随时重建）  →  Redis 的地理索引
```

所以它被淘汰了也不怕，重建一次就好。重建时有个细节：**先整个删掉再写**。否则已经下架的酒店会永远留在图上，查出来再到数据库里找不到人。

**启动时会自动重建一次**。为什么不偷懒不建？因为空索引有个很坑的表现 —— 见下一节。

### 2.3 ★ 一个容易让人抓狂的坑：空索引 ≠ 附近没酒店

假设客人问"周围 3 公里有哪些酒店"，程序回答"一家都没有"。

这可能是两件完全不同的事：

| 真实情况 | 客人看到的 | 该怎么处理 |
|---|---|---|
| 真的附近没有酒店 | 空列表 | 告诉他"附近暂无" |
| **地图索引根本没建** | 空列表（一模一样！） | 应该先重建索引 |

两种情况的返回长得**完全一样**，排查的时候会很折磨人。所以返回值里刻意加了一个字段：

```json
{
  "count": 0,
  "indexedHotels": 0,      ← 0 = 索引是空的，不是"附近没酒店"
  "hotels": []
}
```

只要 `indexedHotels` 是 0，就知道该去重建索引，而不是怀疑数据。

### 2.4 距离怎么保证是对的

这种"算距离"的代码，光看"返回了 5 家酒店"是看不出对错的 —— 全错它也一样返回 5 家。

所以测试里用了**另一套独立实现**的公式（球面距离公式）去验算接口返回的距离，误差必须小于 50 米：

```
酒店 1002   接口说 1.379 公里   自己算 1.379 公里    差 0.2 米
酒店 1003   接口说 2.885 公里   自己算 2.884 公里    差 0.8 米
酒店 1005   接口说 7.047 公里   自己算 7.045 公里    差 1.7 米
酒店 1004   接口说 7.123 公里   自己算 7.121 公里    差 2.2 米
```

最大差 2.2 米 —— 来自地球半径取值的一点区别（Redis 内部用的常数略有不同），完全在预期内。

为了让这个测试有意义，种子数据从 **1 家酒店扩到了 5 家**（杭州真实坐标，到第 1 家酒店的距离分别约 1.4 / 2.9 / 7.1 / 7.0 公里）。只有 1 家酒店的话，半径查询根本没法验证。

## 3. 排序：为什么"先截断再排序"是错的

### 3.1 一个具体的例子

客人说："**5 公里内，给我最便宜的 3 家。**"

有两种做法：

**做法 A（错的）：**
```
先挑出离我最近的 3 家 → 再把这 3 家按价格排
```
这给出的是"**最近那 3 家里最便宜的**"，而不是"方圆 5 公里内最便宜的"。如果最便宜那家在 4.5 公里处，它压根没进候选。

**做法 B（对的）：**
```
先把 5 公里内所有酒店都取出来 → 按价格排 → 取前 3 家
```

这两种做法的结果可以完全不同。用实际数据看：

| 请求 | 做法 B（正确） | 做法 A（偷懒） |
|---|---|---|
| `limit=2&sortBy=price` | 民宿(¥250)、国宾馆(¥300) | 西湖畔(¥400)、国宾馆(¥300) |
| `limit=2&sortBy=distance` | 西湖畔(0km)、国宾馆(1.4km) | 一样 |

所以代码里：**按距离排的话直接从地理索引取前 N 家就行**（它本来就是按距离排的）；**一旦要按评分/价格排，或者要做有房过滤，就必须多取一些候选**，排完再截断。

测试专门钉了这条：两种请求的结果**必须不一样**。这条断言过了，就说明候选确实被放宽了。

### 3.2 什么样的酒店算"能订"

客人给了入住和离店日期，就要过滤掉订不了的酒店。

一家酒店通常有多个房型（大床房、双床房……）。规则是：

> **只要有一个房型在整个入住期间都还有房，这家酒店就算"能订"。**

反过来说，一个房型只要**任何一天**满了，这个房型就不能订了。

实现上只查 **2 条 SQL**，不管有几十家酒店：

```
第 1 条：把候选酒店的所有在售房型都查出来
第 2 条：查出"入住期间某天 已售 + 要订 > 总房量"的房型   ← 也就是"满了的"
剩下的房型都能订；有任意一个能订的房型 → 这家酒店能订
```

**特别注意第 2 条是"找出满了的，然后排除"，而不是"找出能订的"。** 这个方向不能反，原因在下一节。

### 3.3 为什么方向不能反（一个真实的坑）

数据库里"某天卖了几间"的记录是**按需创建**的 —— 没人订过的日期，压根没有记录。

如果写"找出还能订的房型"（用 JOIN 去匹配库存记录），那么**没有任何记录的日期会被漏掉**，看起来就像"这间房不存在"，于是整家酒店被判成订不了。

P0 阶段就踩过一模一样的坑：查房时把"没有库存记录"当成了"剩 0 间"，返回 `available=false`，明明是全新的一天却说订不了。

正确的思路是反过来：**先假设都能订，再排除掉"确定满了的"**。没有记录的日期永远不会出现在"满了的"名单里，自然就被保留了。

## 4. 定期清理

有两类东西会自己慢慢变多，得定期扫掉：

| 东西 | 为什么会变多 | 什么时候能删 |
|---|---|---|
| 防重复提交的记录 | 每次下单都插一行，从来没人删 | 过了有效期（10 分钟）就删 —— 那之后再重试，按新请求处理是合理的 |
| 便签墙上的过期便签 | 正常在作废/支付时会撕掉，但 Redis 抖动、订单被直接删掉时可能残留 | 便签对应的订单已经**不是待支付**了，就撕掉 |

**两类都只删"确定没用"的** —— 这也是为什么清理任务不用太担心安全问题。

### 4.1 一个刚写出来就被测试抓住的 bug

清理功能写完，跑测试发现：**便签确实被清掉了（墙上从 4 张变成 1 张），但接口报告"清理了 0 个"。**

原因很微妙 —— `ZREM` 这个命令的回答**不是"删掉了吗"（true/false），而是"删掉了几个"（一个数字）**。所以这样写永远不会成立：

```java
// 错：Boolean.TRUE.equals(数字) 永远是 false
if (Boolean.TRUE.equals(redis.opsForZSet().remove(key(), s))) { removed++; }
```

```java
// 对：判断删掉的个数是不是大于 0
Long n = redis.opsForZSet().remove(key(), s);
if (n != null && n > 0) { removed++; }
```

功能其实是对的，只是**计数是错的**。这种 bug 最阴险 —— 从外部看"清理成功了"，但监控和日志全是 0，出问题时完全看不到。

顺手把全项目同类写法都搜了一遍，另外三处（`setIfAbsent` / `putIfAbsent` / `add`）确实返回的是 true/false，没问题。

### 6.2 四个最关键的证据

**① 真的到点自己释放了**

```
把某单的提醒时间改成 5 秒前（模拟"已经到点了"）
→ 2 秒内它就变成"已作废"，房退回去了，便签也撕掉了
```

**② 同一单处理两次不会重复退房**

```
把同一张便签再贴回去
→ 状态还是"已作废"，剩余房数不变，台账也没被重复标记
```

**③ 排序和截断的顺序是对的**

```
"最便宜的 2 家" → 民宿(¥250)、国宾馆(¥300)
"最近的 2 家"   → 西湖畔(0km)、国宾馆(1.4km)
两者不同 → 证明候选确实放宽了（见 §3.1）
```

**④ 清理不会误伤**

```
墙上 4 张便签：待支付 / 已支付 / 不存在的订单 / 乱码
→ 清掉 3 张，待支付那张留着
→ 留着那张之后仍然能正常到点释放
```

## 7. 踩过的坑

按"花了多久才发现"排序：

### ① `$base` 把 API 地址冲掉了（查了半天）

测试脚本里我写了个变量叫 `$base`：

```powershell
$base = "/booking/hotel/nearby?longitude=..."
```

而公共测试库里 `$Base` 是 **API 地址**（`http://127.0.0.1:8080`）。PowerShell 的变量名**不分大小写** —— 于是 API 地址变成了一个 URL 路径。

症状：所有请求都返回"连不上"，我甚至先去查了端口和容器，都好好的。

现在加了守卫：一旦发现 API 地址不是以 `http://` 开头，立刻抛出指名道姓的错误，不用再去猜。

> 这已经是第三次撞库里的变量名了（前两次是 `$fail` 计数器和 `$R` / `$Rd` 别名）。
> **共同点都是"名字太普通"** —— `$base`、`$fail` 这种词，谁都想用。

### ② 清理做了，但报告 0 个（见 §4.1）

`ZREM` 的回答是"删掉了几个"，不是"删掉了吗"。

### ③ GET 参数校验失败返回 500 而不是 400

这个坑在 Spring 里有点绕：

- `@RequestBody`（POST 的 JSON 体）校验失败 → 抛 `MethodArgumentNotValidException` ✓ 我接住了
- **`@ModelAttribute`（GET 的查询参数）校验失败 → 抛 `BindException`** ✗ 我没接住，掉进了兜底的 500

而且前者是后者的**子类**（反过来说不成立），所以接住子类不等于接住父类。

### ④ MySQL 把 `ON` 认成了 JOIN 的条件

想写"批量插入，重复就更新"：

```sql
FROM seq CROSS JOIN (...) rt ON DUPLICATE KEY UPDATE price = VALUES(price)
                           ↑ 这个 ON 被当成 JOIN 的 ON 了，直接语法错
```

改成把要关联的那一列**放进递归查询里**，完全不用 JOIN，问题自然消失。

### ⑤ 故意搞脏的测试数据没修回来

有个用例为了验证"缓存真的在拦请求"，**故意**把某天的库存缓存改成了"满"。用完忘了修回来。

当时跨月测试用的是另一天，相安无事。结果日期一滚动，两者**撞到了同一天** —— 跨月下单被这条假数据挡成 409，看起来像功能坏了。

现在改完立刻从数据库修回来。**故意破坏状态之后要收拾干净。**

### ⑥ 字符串里的双引号 / 文件丢了 BOM

```powershell
"...要能和"附近没有酒店"区分开..."    ← 这一行被截断了
```

报的是 `Unexpected token`，指着一行看起来完全正常的代码。

而**文件丢了 BOM**（一个编码标记）时的报错**长得一模一样** —— 中文被打碎成幽灵字符，同样报 `Unexpected token`。这两种原因完全不同的错误，光看报错根本分不清。

所以写了个 `test/check-syntax.ps1`，把两件事**分开报**：

```
[FAIL] xxx.ps1  -- 缺 UTF-8 BOM（PS 5.1 会按 GBK 解析，中文会打碎成幽灵字符）
[OK]   p2_cleanup_test.ps1
```

## 9. 下一步：P3

P3 是 **缓存三兄弟（本地缓存 / Redis / 数据库）+ 分布式锁**。

按你说的，**先在单实例下做完，多实例的事之后再说**。单实例的好处是：本地缓存不会有"别的实例改了而我不知道"的问题 —— 可以先把多级缓存的骨架和读写逻辑写清楚。

单实例阶段要解决的三个老问题：

| 问题 | 现象 | 常规解法 |
|---|---|---|
| **缓存穿透** | 查一个根本不存在的房型，每次都穿到数据库 | 把"查不到"也缓存一下 / 布隆过滤器 |
| **缓存击穿** | 某个热点 key 刚好过期，瞬间一堆请求同时去数据库重建 | 只让一个请求去重建，其它等着（单飞） |
| **缓存雪崩** | 一大批 key 同时过期，数据库被瞬间压垮 | 过期时间加随机抖动 |

再加上**分布式锁**（`SET NX EX`）—— 单实例下它更像是"给以后的自己留好接口"，顺便可以拿来演示锁的正确用法（谁加的锁谁释放、超时怎么办）。
