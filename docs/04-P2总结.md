## 1. ★ 延迟队列：为什么必须是两条路径

### 1.1 先看它解决什么

P1 及之前，"超时未支付"只能靠手动：

```
POST /booking/expire-scan  →  没人调它，订单永远不会过期，库存被永久占着
```

P2.1 把它变成**秒级自动**：下单时把 `bookingId` 按「触发时刻」放进一个 Redis ZSet，一个每秒跑的任务把它捞出来处理。

```
key    hotel:delay:order      (ZSet)
score  触发时刻的 epoch 毫秒
member bookingId
```

### 1.2 ★ 核心判断：它是"待办任务"，不是缓存

这是 P2 里最值得记住的一条：

| | 库存缓存（P1） | 延迟队列（P2） |
|---|---|---|
| 本质 | 从 DB 派生的**加速层** | **待办事项本身** |
| 丢了会怎样 | 一次 cache miss，退化成纯 DB 路径 | **订单永远不会超时释放，库存被永久占着** |
| 有没有报错 | 没有 | **也没有** |

所以服务器 Redis 的淘汰策略从 `allkeys-lru` 改成了 **`volatile-lru`**：

- `allkeys-lru` 会淘汰**任何**键 —— 包括刻意不设 TTL 的队列
- `volatile-lru` 只淘汰**设了 TTL** 的键 —— 队列不设 TTL 就天然受保护；设了 24h TTL 的库存缓存照旧可淘汰

一行配置，正好让两类数据各归其位。

### 1.3 但仅靠这一点不够 —— 双保险

```
① ZSet 精确触发（每 1 秒）        ← 主路径，秒级
② DB 扫表（每 5 分钟）            ← 兜底，慢但一定能捞回来
```

第二层不能省。**Redis 重启、被清空、入队时恰好失败**，任务都会静默丢失，而扫表是唯一能发现"有订单该过期了但没人处理"的机制。

两条路径都安全重复执行，因为 `expireBooking()` 内部用条件 UPDATE（`WHERE booking_status = 10`）改状态 —— 只有打中 1 行的那个才算成功。

> 这条兜底**真的被用上过一次**：P2.1 部署完首次启动，日志里出现
> 「兜底扫表释放了 5 个超时订单」，那是 P1 时期留下的待支付订单（当时还没有队列）。

### 1.4 原子认领：谁删掉谁处理

`ZRANGEBYSCORE` + `ZREM` 放在**同一个 Lua 脚本**里：

```lua
local members = redis.call('ZRANGEBYSCORE', key, '-inf', now, 'LIMIT', 0, limit)
for i = 1, #members do
  if redis.call('ZREM', key, members[i]) == 1 then
    claimed[#claimed + 1] = members[i]
  end
end
return claimed
```

如果分成两条命令，两个消费者会拿到同一批成员、各处理一遍。放进一个脚本后，Redis 单线程执行保证中间不会被插入 —— **谁删掉谁处理**，多实例安全。

这跟 P1 台账释放的"一次性令牌"是同一个思路，只不过令牌换成了 `ZREM` 的返回值。

### 1.5 入队必须在事务提交之后

复用 P1 的 `afterTransaction`。否则订单回滚了，队列里却留了一条 —— 到点触发时发现订单不存在，白跑一趟，队列还脏了。

出队（支付 / 取消 / 失效）同样在提交后做，避免到点白跑。

## 2. ★ GEO：另一个"可重建的派生索引"

```
key    hotel:geo:all          (GEO，member = hotelId)
写入   GEOADD    hotel:geo:all <lng> <lat> <hotelId>
查询   GEOSEARCH hotel:geo:all FROMLONLAT <lng> <lat> BYRADIUS <km> km ASC WITHDIST
```

和 P1 的库存缓存是**同一个定位**：从 `hotel` 表派生、可随时重建、被淘汰不影响正确性。用现代的 `GEOSEARCH`，不是已弃用的 `GEORADIUS`。

**为什么用单个 key 而不按城市分**：跨城市、跨城市边界都能搜到；数据量小完全够用。按城市分 key 会让"城市边界附近"漏掉。

**重建时先 `DEL` 再写**：否则下架/删除的酒店会永远残留在索引里，查出来再去 DB 找不到对应行。

**启动时预热**（`hotel.nearby.rebuild-on-startup`）：索引是可重建的派生数据，但**"空索引"会让附近查询静默返回空列表** —— 与其让调用方困惑，不如启动时就建好（5 家酒店，几十毫秒）。失败不影响启动。

### 2.1 一个刻意加的字段：`indexedHotels`

`hotels` 为空有两种**完全不同**的原因：

| 情况 | `count` | `indexedHotels` |
|---|---|---|
| 索引没建（被淘汰/没预热） | 0 | **0** ← 调 rebuild |
| 附近确实没有酒店 | 0 | **> 0** |

不区分的话，排查时会怀疑人生。

### 2.2 距离是怎么验的

不是"数量对了就算过"。测试里用一份**独立实现**的 haversine（R=6371.0088 km）去验算 API 返回的 `distanceKm`，误差必须 < 50 m：

```
[OK ] hotel 1001  API= 0.000 km  haversine= 0.000 km  差=0.0000 km
[OK ] hotel 1002  API= 1.379 km  haversine= 1.379 km  差=0.0002 km
[OK ] hotel 1003  API= 2.885 km  haversine= 2.884 km  差=0.0008 km
[OK ] hotel 1005  API= 7.047 km  haversine= 7.045 km  差=0.0017 km
[OK ] hotel 1004  API= 7.123 km  haversine= 7.121 km  差=0.0022 km
```

最大偏差 2.2 m，来自地球半径取值（Redis 内部用 6372797.56 m）。

为此把种子数据从 **1 家酒店扩到 5 家**（杭州真实坐标，到 1001 的距离分别约 1.4 / 2.9 / 7.1 / 7.0 km），否则半径查询没法验证。

## 3. ★ 排序与截断的顺序

### 3.1 顺序不能乱

```
GEO 取候选  →  有房过滤  →  排序  →  截断
```

### 3.2 最容易写错的地方：候选数量

如果写成"先按距离取 `limit` 个，再排序"，得到的是**「最近 N 家里最便宜的」**，而不是**「范围内最便宜的 N 家」**：

| 请求 | 正确答案 | 偷懒实现会给出 |
|---|---|---|
| `limit=2&sortBy=price` | `[1004, 1002]`（¥250、¥300） | `[1002, 1001]`（根本没 1004） |
| `limit=2&sortBy=distance` | `[1001, 1002]` | 一样 |

所以**非距离排序或有房过滤时，GEO 必须多取候选**（`limit × 5`，上限 200），排完再截断。

测试专门钉了这一条：两种请求的结果**必须不同**，这条断言过了就证明候选确实被放宽了。

### 3.3 有房过滤：只跑 2 条 SQL

```
① 取出候选酒店的所有在售房型
② 取出「区间内某天 已售 + 要订 > 总房量」的房型     ← 即"被占满的"
剩下的房型都可订；只要有一个可订房型，这家酒店就算可订
```

**必须用「找出被占满的再排除」，而不是「找出可订的」**：

区间内没有库存行的日期，等于「还没人订过」（sold=0），**不该被当成不可订**。用 JOIN 去找"可订的"会把这类日期漏掉（这正是 P0 那个 `available=false` bug 的同款陷阱）。

另外 `total_rooms < roomCount` 的房型直接算不可订（总房量都装不下）。

两条 SQL 的数量都不随酒店数增长 —— 不是 N+1。

### 3.4 次级排序统一用距离

同评分 / 同价格时按距离决胜，结果稳定可预期。实测价格排序里，西湖畔与湖滨银泰同为 ¥400，因为距离更近排在前。

## 4. 定期清理

P2.4 收掉两类"会无限增长 / 会悄悄残留"的数据：

| 对象 | 为什么会涨/残留 | 清掉的依据 |
|---|---|---|
| `idempotent_record` | 每次下单插一行，从来没人删 | `expire_time < now`（= 创建时间 + TTL，过了幂等窗口就不可能再被重试命中） |
| `hotel:delay:order` 成员 | 正常在终态时 `ZREM` 自己，但 Redis 抖动 / 订单被直接删掉时会残留 | member 对应的订单**不处于待支付**，或根本不存在，或成员不是合法数字 |

**两类都只删"确定没用"的。** 幂等记录过了 TTL 就过了契约窗口；延迟队列里已终态的任务永远不会再被处理。

分批删（默认 5000/批，最多 10 轮），避免一次锁太多行。

### 6.2 P2 的四个决定性证据

**① 延迟队列真的到点自动释放**

```
把 bookingId 的 score 改成 5 秒前（模拟已到期）

```

**② 重复触发不重复释放**

```
把同一个 bookingId 再 ZADD 回去

两者不同 → 证明候选被放宽了
```

```
队列 4 个成员：待支付 / 已支付 / 孤儿 / 非法
→ 清掉 3 个，待支付的保留
→ 被保留那单之后仍能正常超时释放
```

## 7. 这一阶段踩过的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | `FROM ... CROSS JOIN (...) rt ON DUPLICATE KEY UPDATE ...` 语法错 | MySQL 把 `ON` 当成了 **JOIN 的 ON 条件**。改成把关联列放进递归 CTE，彻底不用 JOIN |
| 2 | GET 参数校验失败返回 **500** 而不是 400 | `@ModelAttribute` 抛的是 `BindException`，而 `MethodArgumentNotValidException`（`@RequestBody` 用的）接不住它。Spring 6 里前者是后者的**父类**，反过来不成立 |
| 3 | 清理"做了但计数报 0" | `ZSetOperations.remove()` 返回 **`Long`**（删掉了几个），不是 `Boolean`。`Boolean.TRUE.equals(...)` 恒为 false |
| 4 | 测试里 `$base = "..."` 让所有请求变成 `HTTP -1` | PowerShell 变量名**不区分大小写**，撞上了库里的 API 地址 `$script:Base`。已加运行时守卫 |
| 5 | 故意污染的测试数据没修回来，撞上别的用例 | 曾把"锚点+21 天"的缓存改成满值不修；日期一变撞上跨月测试那天，下单被假数据挡成 409 |
| 6 | 字符串里塞 ASCII 双引号 / 丢 BOM | 两种错误报错**长得一模一样**（`Unexpected token`）。写了 `test/check-syntax.ps1` 分开报 |

第 3 条补充：顺手全项目搜了同类写法，另外三处（`setIfAbsent` / `putIfAbsent` / `add`）确实返回 `Boolean`，没问题。

第 4 条是第三次撞库里的变量名了（前两次是 `$fail` 计数器和 `$R`/`$Rd` 别名）。**共同点都是"名字太普通"**。

## 9. 通往 P3

P3 = **缓存三兄弟 + 分布式锁**。

| 位置 | 现在 | P3 之后 |
|---|---|---|
| 库存读取 | 只有 Redis 一层 | 加 Caffeine 本地缓存（多级） |
| 缓存击穿 | 懒加载，冷 key 并发回源 | 单飞（single-flight）/ 逻辑过期 |
| 缓存穿透 | 不存在的房型每次都回源 DB | 空值缓存 / 布隆过滤器 |
| `@Scheduled` | 多实例会各跑一遍 | 分布式定时任务（或 `SET NX` 抢占） |
| 关键临界区 | 靠条件 UPDATE | `SET NX EX` 分布式锁 |

**P3 第一个要想清楚的事**：加了本地缓存之后，"取消订单"要不要**广播失效**？单实例无所谓，多实例就必须处理 —— 否则 A 实例的本地缓存会一直认为那间房还占着。

这是 P3 的核心矛盾，比 P2 的"队列会不会丢"更难，因为**它没有 DB 兜底**：本地缓存过期前，读到的就是错的。
