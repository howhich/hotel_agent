# P4 总结：从"能跑"到"能上线"

> 前三阶段（P0–P3）解决的是**业务正确性**：区间库存不会超卖、改期不会算错、
> 缓存不会脏、订单不会永远挂着。
>
> P4 解决的是另一类问题：**这个服务敢不敢让陌生人调。**

先说结论。做完 P0–P3 时，这个项目有一个致命问题，一句话就能说清：

> **`userId` 是前端传的。**

也就是说，任何人只要改一下请求体里的 `userId`，就能：

- 冒充别人下单
- 看别人的订单
- 取消别人的订单

业务逻辑再严谨也没用 —— 因为**"你是谁"这件事，一直是客户端说了算**。

P4 就是把这个洞堵上，然后在此基础上接入 Agent。

## 一、P4.1：先搞清楚"你是谁"

### 1.1 token 存 Redis，还是签 JWT？

这是唯一需要认真选的地方。

| | Redis 随机 token（选了这个） | JWT |
|---|---|---|
| 能强制下线吗 | ✅ 删 key 立刻失效 | ❌ 签出去了就收不回来 |
| 能查谁在线吗 | ✅ | ❌ |
| 能限制单点登录吗 | ✅ | ❌ |
| 每个请求的代价 | 多一次 Redis 查询 | 无 |

**为什么选 Redis**：这个项目本来就重度依赖 Redis（库存缓存、幂等、延迟队列、GEO）。
再依赖一次，边际成本几乎为零；而"能随时踢人下线"在真实系统里是刚需 ——
用户改密码、账号被盗、客服封号，都需要立刻失效。

JWT 唯一的优势是"无状态、不查库"，但本项目每个请求本来就要碰 Redis，
省不掉那一次往返。所以选它没有悬念。

```
key    hotel:token:{32 位随机串}
value  userId:role
TTL    2 小时
```

### 1.2 两句话必须一模一样

登录失败时：

```
密码错      → 401 {"message":"用户名或密码错误"}
用户不存在  → 401 {"message":"用户名或密码错误"}      ← 一字不差
```

**为什么？** 如果两句话不一样，你就送给攻击者一个**用户名枚举接口**：
他拿一个假密码，把用户名列表刷一遍，看哪些返回"密码错"、哪些返回"用户不存在"，
就免费得到一份真实账号名单。

测试里专门断言了这两条消息**完全相同**。

### 1.3 ★ ThreadLocal 用完必须 clear

`UserContext` 是用 `ThreadLocal` 存的。而 **Tomcat 的线程是池化复用的**。

```java
// 忘写这一行的后果：
// 请求 A（用户 9001）用完线程 T，没清
// 请求 B（用户 9002）恰好复用线程 T
//   → B 读到的 UserContext 是 9001
//   → B 的所有操作都以 9001 的身份执行
```

这是最经典的越权漏洞之一，而且**极难通过测试发现** ——
因为本地调试时线程复用不明显，上线后才会偶发。

所以 `AuthInterceptor.afterCompletion` 里无条件 `UserContext.clear()`。

### 1.4 一个坑：拦截器写的 401，PowerShell 读不到 body

现象很怪：

```
状态 401，Content-Length: 73
但 GetResponseStream() 读到 0 字节
用 curl 拿 → 完整 body 就在那儿
```

说明**服务端是对的**，是客户端读不到。原因：拦截器 `return false` 之后，
Spring 不再走正常的响应处理流程，缓冲区没有被及时刷出去。

修法是显式 `response.flushBuffer()`。这行代码不写也能"工作"（curl 能拿到），
但它会让一部分客户端拿到空 body —— 属于那种"在你机器上没问题"的坑。

## 二、P4.2：他不是你的

登录解决了"你是谁"，但没解决"这个单子是不是你的"。

```
GET /booking/{别人的订单号}   → 当时照样返回 200
```

### 2.1 校验放在哪里？——放在"必经之路"上

用户侧访问订单只有四个入口：

```
查详情 / 支付 / 取消 / 改期
```

它们全都走 `requireBooking(bookingId)`。所以归属校验**放在这个方法里**，
写一次就全覆盖，以后新增入口也不会漏。

```java
private Booking requireBooking(Long bookingId) {
    ...
    assertOwnership(b);      // ← 就这一行，四个入口全部受保护
    return b;
}
```

这叫**默认安全**：新代码只要走这条路就自动被保护；
想绕过校验，必须特意去用 mapper。

> ⚠️ 但内部路径（定时任务、超时释放）**不能用它** ——
> 那些场景没有登录用户，`UserContext.requireUserId()` 会直接抛 401。
> `expireBooking` 就是自己查 mapper 的，注释里写清了原因。

### 2.2 越权返回 403 还是 404？

这是个真实的权衡：

| 返回 | 含义 | 好处 | 坏处 |
|---|---|---|---|
| 403 | 存在，但不是你的 | 前端提示清楚、排查方便 | 泄露"这个单号存在" |
| 404 | 就当不存在 | 不泄露存在性 | 用户和客服都会困惑 |

**这个项目选了 403**，理由：订单号是**雪花 ID**，不可枚举。
攻击者猜不出有效单号，"泄露存在性"的价值极低；
而 403 对前端（"这不是你的单"）和排查都友好得多。

测试里也钉了这个顺序：

```
不存在的单号  → 404   （先查存在性）
别人的单号    → 403   （再验归属）
```

### 2.3 ★ 被拦下时不能有副作用

这条很容易被忽略，但很关键。B 尝试取消 A 的订单，返回 403 之后要确认：

```
订单状态 = 10     （还是待支付）
库存     = 1      （没被退）
check_in = 原值    （没被改）
```

如果校验写在业务逻辑**后面**，就会出现"抛异常了，但库存已经退了"这种
**部分生效**的状态 —— 比不做校验更糟。

## 三、P4.3：Agent —— 模型只用在一个地方

这是整个 P4 里最需要判断力的部分。

### 3.1 一个反直觉的决定

大多数 Agent 教程的做法是：把工具列表丢给模型，让它自己决定调什么、传什么参数、
然后循环。

这个项目**没有**这么做。它只让模型干一件事：

```
用户这句话 → {意图, 槽位}
```

其余全部是代码：

```
用户一句话
  → ① 模型解析成 {意图, 槽位}      ← 只有这一步用模型
  → ② 合并会话里已有的槽位（多轮）
  → ③ 缺什么就用模板话术追问
  → ④ 齐了调工具：查酒店 → 查可订 → 报价 → 出候选
  → ⑤ 存成草案，等用户确认
  → ⑥ 确认后下单
```

**为什么？** 因为模型不擅长算数，而且**每次算得还不一样**。

- "住两晚"是几晚？→ 模型换算（它很擅长，实测很准）
- 总价多少钱？→ **代码算**（用价格日历逐晚累加）
- 这个房型还有房吗？→ **代码查**（复用既有的 `checkAvailability`）
- 该订哪个？→ **代码排序取最优**

如果你让模型去算总价，它可能今天算对、明天算错，而且你没法写测试。
如果你让它"自己决定调哪个工具"，那它可能漏调一步，你也很难复现。

> **把模型用在"读懂人话"这一件事上，是这一阶段最重要的设计判断。**

实测这条链路的效果：

```
"帮我订杭州11月20号住两晚，要大床房，1间"
→ BOOK / 杭州 / 2026-11-20 → 2026-11-22 / 1间 / 大床

"明天杭州有房吗"
→ QUERY / 杭州 / 2026-11-12         ← 相对日期换算正确

"算了不订了"
→ CANCEL

"我想订房"
→ BOOK / 缺 city、checkIn、checkOut   ← 知道自己缺什么
```

### 3.2 多轮：槽位是中间层

用户很少一次把话说全。"我想订房" → 缺城市、缺日期。

如果每句话都直接查库，就会查出一堆无意义的结果。
正确做法是先解析成**字段**（槽位），再看缺什么、缺就问，齐了才查。

```
会话状态（Redis，TTL 30 分钟）
  intent   BOOK
  slots    { city: 杭州, checkIn: 2026-11-20, checkOut: 2026-11-22, roomCount: 1 }
  history  最近 10 轮
  draft    待确认的草案
```

实测三句话攒齐：

```
"我想订房"        → COLLECTING，问城市和日期
"杭州"            → COLLECTING，记住了城市
"11月20号住两晚"  → SEARCHED，city 从上一轮带过来
```

### 3.3 模型不可全信

即使只让它解析意图，也得防它出错：

| 它可能出什么错 | 怎么办 |
|---|---|
| 给一个过去的日期 | 服务端校验 → 清掉日期并追问"日期我没理解对" |
| 离店 ≤ 入住 | 同上 |
| 返回坏 JSON | 降级为 CHITCHAT，不猜、不硬解析 |
| 把日期格式写错 | 同上，当作缺失处理 |

**关键点：校验放在服务端，不是"信任模型"。**

## 四、P4.4：HITL —— 不让模型决定订单内容

Agent 查到候选之后停下来，等用户说"确认"。

### 4.1 ★ 三条安全线

```
用户: "确认"
   ↓
① 下单内容只来自【草案】——不来自用户这句话，也不来自模型
② 身份只来自 UserContext ——模型永远不参与
③ 草案用完即作废 ——连点两次"确认"不会下两单
```

**第 ① 条为什么最重要？**

假设确认时去解析用户那句话：

```
用户: "订那个 100 块的"
```

模型可能被引导去订**另一个房型**。而草案是**服务端自己查出来、自己算过价**的那一份，
它才可信。

测试里有一条硬断言：

> 手工造一个草案指向 **2001**（高级大床房）；
> 而"重新搜一次"会选中 **2003**（园景大床房，更便宜）。
> 说"确认"后，DB 里订的必须是 **2001**。

如果订成了 2003，说明它偷偷重搜了一遍（或者听了用户的话）—— 那就不安全。

### 4.2 草案为什么要过期

草案是"**某一刻的**房态 + 价格"。放了 10 分钟再确认：

- 房可能没了
- 价格可能变了

用户按旧价预期，却按新价付钱 —— 这是投诉的高发区。

所以草案带 `createdAt`，超过 5 分钟就作废：

> 那个方案是 30 分钟前查的，价格和房态可能变了，我不敢直接下单。要我重新查一遍吗？

### 4.3 "房没了"返回 200 还是 409？

`createBooking` 房量不足会抛 **409**。但 Agent 把它**吞掉**，返回 **200 + 一句人话**：

> 没订上：房量不足。要我重新查一下还有哪些可订的吗？

理由：用户这一轮对话是**成功的**（意图理解对、参数齐、工具调通了），
只是业务上没订上。把 409 抛给前端，前端会以为"Agent 接口坏了"。

**接口的语义层和业务的语义层要分开。**

## 五、P4.5：运维接口要管理员

最后一件事，是 P4 收尾时才补上的。

这些接口能改价格、重建缓存、清数据：

```
POST /booking/inv/rebuild          重建库存缓存
POST /booking/hotel/price/update   改价
POST /booking/maintenance/cleanup  清数据
POST /booking/expire-scan          批量释放订单
```

在 P4.2 之前，**任何登录用户都能调**。这比越权查订单还严重 ——
一个普通用户可以改所有人的价格。

修法：加一个 `AdminInterceptor`，和"登录拦截器"职责分开：

```
① AuthInterceptor   （全站）      → 你是谁
② AdminInterceptor  （运维路径）  → 你能不能
```

注册顺序就是执行顺序，所以 Auth 一定先跑（否则 Admin 判断时拿不到用户）。

### ★ 这里有个容易漏的约定

新增一个运维接口时，如果忘了往 `WebConfig` 里加路径，
它就会变成"任何登录用户都能调"，**而且不会有任何报错提醒你**。

所以定了个约定：**所有运维/调试接口统一放在这几个前缀下面**

```
/booking/inv/**           库存缓存
/booking/maintenance/**   清理
/booking/delay/**         延迟队列
/booking/hotel/geo/**     GEO 索引
/booking/hotel/price/**   改价
/booking/expire-scan      手动释放
```

这样 `WebConfig` 里那串清单就是**完整的权限边界**，一眼能审。

## 六、★ 这一阶段挖出的三个跨阶段 bug

这部分是 P4 最有价值的副产物。改鉴权、跑全量回归，把前面阶段埋的问题都翻出来了。

### 6.1 跨用户幂等串单（P4.1 自己引入的，P4.4 发现）

**现象**：两个不同用户提交**完全相同的请求体**，第二个人会拿到第一个人的订单号。

**原因**：

幂等指纹原来只序列化**方法入参**：

```java
String json = objectMapper.writeValueAsString(keep.toArray());
```

而 P4.1 之后，`userId` **不再从入参取**（改成从 token 取）。于是：

```
用户 A: {hotelId:1001, roomTypeId:2001, checkIn:X, checkOut:Y}
用户 B: {hotelId:1001, roomTypeId:2001, checkIn:X, checkOut:Y}   ← 完全相同
        ↓
   同一个幂等键  →  B 被当成"重复提交" → 回放 A 的 bookingId
```

**后果**：既泄露了别人的订单号，又让 B 少订了一单。

**修法**：指纹里加上登录用户前缀。

```java
String userPart = currentUserPart();      // "u9001_"
return userPart + "f:" + sha256Hex(json).substring(0, 32);
```

> **教训**：当你改变"某个值的来源"时，要检查**所有读过它的地方**。
> `userId` 从"入参"变成"上下文"，业务代码改了，但幂等指纹没改 —— 它还在用入参。

### 6.2 Redis 一抖就 500（P1 / P3 埋的，P4.2 发现）

**现象**：并发测试里 3 个请求返回 500。

```
QueryTimeoutException: Redis command timed out
  at InventoryCacheService.loadWithSingleFlight(...:324)
```

**原因**：这个文件里其他每一处 Redis 调用都做了降级，**唯独两处裸露着**：

1. 等待循环里的 `hasKey`
2. `loadRangeFromDb` 里逐天写缓存的 `putIfAbsent` + `expire`

第 2 处尤其说不通：**DB 已经查到了，调用方拿着结果照样能干活**，
单纯因为"写缓存失败"就让下单 500，完全没道理。

**修法**：两处都吞异常 + 记日志。

> **一条值得记住的原则**：
> **缓存的职责是加速。它坏了应该退化成"慢"，绝不能变成"错"。**

**顺带**：Redis 客户端超时从 3 秒放宽到 10 秒。
因为开发环境经 SSH 隧道访问远端 Redis，十几路并发时单条命令可能排队几秒。
超时会连锁反应：token 校验失败 → 401（明明登录了却说不认识你）。

### 6.3 测试库的"沉默失败"（P4.3 发现）

**现象**：跑全量回归，**前三个套件 66 个断言集体失败**，每条 `actual` 都是空的。

单独重跑，全绿。

**真正的问题在测试库**：

```
ResetTestData 先清 hotel:*（连 token 一起删）→ 重新登录
登录失败了却【不吭声】
→ 后面几十个断言全部 401
→ 看起来像"业务代码全坏了"
```

**修法**：

- `Login` 失败直接抛错
- `ResetTestData` 里重试 3 次，仍失败就抛出明确消息

> 宁可炸在一行清楚的错误上，也不要制造 66 个看不懂的假失败。
> **测试基础设施的失败必须响亮。**

## 七、测试

```
P4 新增断言
  p4_auth_test         24 项   登录 / token / 防枚举 / 请求体 userId 被无视
  p4_authz_test        25 项   越权 403 / 零副作用 / 运维接口要管理员

全量：13 个稳定套件 320 项 + 2 个演示套件 42 项
```

### 最有说服力的几条

```
① token=9001，但请求体里写 userId=9002
   → DB 里这笔订单的 user_id 是 9001        ← 请求体的值被无视

② B 对 A 的订单：查/支付/取消/改期/看列表
   → 全部 403，且状态、库存、日期都没变     ← 零副作用

③ 草案指向 2001，重搜会选 2003
   → 确认后订的是 2001                      ← 内容来自草案

④ 普通用户调 /booking/inv/rebuild → 403
   管理员调 → 200                            ← 功能级权限
```

### 关于两个 Agent 套件

它们依赖**外部大模型**。定位是**证明这个项目接入了 Agent 能力**
（意图理解、工具调用、多轮、人工确认），**不是**压并发、扛回归。

所以它们被明确标成"演示套件"，不作为回归门槛。
没配 key 时会打印 `[SKIP]` 退出 0。

> 这也是一个设计判断：**不要让一个不受你控制的外部依赖，决定你的回归能不能过。**

## 八、P4 做对了什么

| 决定 | 为什么对 |
|---|---|
| token 存 Redis 而不是 JWT | 能踢人下线，代价几乎为零 |
| 归属校验放在 `requireBooking` | 默认安全，新入口不会漏 |
| 越权用 403 而不是 404 | 雪花 ID 不可枚举，403 更清楚 |
| 只让模型做意图解析 | 结果确定、可测试、不花钱 |
| 草案 + 三条安全线 | 模型和用户的话都不能决定订单内容 |
| 会话/缓存失败都降级不抛错 | 体验问题不该变成 500 |
| 运维接口单独一个拦截器 | 权限边界一眼能审 |
| Agent 套件不当回归门槛 | 外部依赖不该绑架你的质量门 |

## 九、如果继续做下去

按价值排序：

1. **把 502 查清**：应用侧到 DeepSeek 偶发失败，日志里已有底层异常，
   先确认是限流（429）还是超时，再决定重试策略
2. **Agent 支持取消/改期**：现在会如实说"还不会"，但接口都是现成的
3. **接真实支付**：现在 `pay` 只改状态
4. **P5：工单与检索**：Mongo + ES 容器一直开着没用上，
   正好接一个"客服工单 + 中文全文检索"
5. **把 PowerShell 端到端测试补一份 JUnit**：现在的内容（并发、死锁、缓存）
   只有打接口才看得见，但 JUnit 更适合进 CI

## 十、一句话收束

P0–P3 让这个服务**算得对**。

P4 让它**敢让陌生人调**。

而这两件事之间的差距，往往比"再加一个功能"大得多 ——
因为功能不够只是少了个东西，**身份靠前端传则是所有人都能当任何人**。
