## 1. 三个毛病分别是什么

先把话说白。缓存就像前台的一本**名册**，真正的档案在后面的**档案室**（数据库）。

- **穿透**：有人拿个**根本不存在的名字**来问。前台跑一趟档案室，回来两手空空。他再来问，前台还是跑一趟 —— 因为前台**不记得"这个名字查过、没有"**。
- **击穿**：名册上**某一个热门的名字**那一页正好到期被抽走了。这时候一百个人同时来问这**同一个人**，一百个人同时往档案室跑。
- **雪崩**：不是一页，是**整本名册的每一页都在同一分钟到期**。到点，所有人同时往档案室冲。

差别就在**规模和时机**：

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 问的是什么 | 一个**不存在**的东西 | 一个**真实的热点** | **一大批真实**的东西 |
| 什么时候出问题 | **一直**，每次都白跑 | 缓存**刚过期那一瞬** | **同一时刻到点** |
| 后果 | 数据库被无意义的查询占满 | 一个热点打爆数据库 | 数据库整体被打爆 |
| 解法 | 记住"查过了，没有" | 只放一个人去查 | 让过期时间错开 |

**三者都只影响"性能"，不影响"正确性"** —— 这一点很重要，它决定了后面所有的取舍都应该是"宁可慢一点，也不能错、不能卡死"。

## 2. P3.1 穿透：给"查不到"也记一笔

### 2.1 问题长什么样

```
GET /booking/123456789012345678     ← 随手编一个订单号
→ 查库 → 没有 → 404
再刷 1000 次 → 查库 1000 次
```

数据库每次都白查一遍，因为它没有"没找到"的记忆。按 id 点查的接口都有这个问题：订单详情、房型校验、酒店查询。

### 2.2 做法

查证"不存在"之后，把它记到 Redis 里一小段时间（默认 60 秒）。这段时间里同样的 id 直接返回 404，**一次数据库都不碰**。

### 2.3 ★ 只记"不存在"，不缓存正本

这是这一节最关键的取舍。如果连"正本数据"也缓存，会多出两件麻烦事：

1. **数据改了，缓存什么时候失效？** —— 立刻多出一整类 bug
2. **写路径（下单、改期）可能读到过期的 `total_rooms`** —— 危险

只记"不存在"这两条风险都不存在：命中正本永远走数据库，拿到的永远是最新的。所以 **P3.1 一行"缓存一致性"的代码都没写**。

### 2.4 ★ 为什么 TTL 必须很短（60 秒）

"不存在"这个判断**有可能过时**：后台补录数据、数据修错了再改回来。

TTL 短，就把"记错了"的代价限制在 60 秒内 —— 到点自动恢复，不需要人工清缓存。**这是这个方案唯一的取舍点，也是它安全的原因。**

### 2.5 一个刻意的设计：所有方法都吞异常

它只是"省一次数据库查询"的优化。Redis 挂了就退化成"每次都查库"，绝不能因为它坏了让接口报错。

### 2.6 怎么证明"真的没查库"

这里踩了个大坑，值得单独说。

我先用 MySQL 的 `Com_select`（SELECT 语句总数）做前后差值，结果量出来**每个请求都有 1~2 次 SELECT**，一度以为缓存没生效。

开了 `general_log` 抓真话才看清：

```
Request 1:  INSERT 幂等记录 → SELECT room_type → ROLLBACK → DELETE 幂等记录
Request 2:  INSERT 幂等记录 → （没有 room_type 查询！）→ ROLLBACK → DELETE 幂等记录
```

**那 1~2 次是 JDBC 驱动自己发的 `SELECT @@session.transaction_read_only`**，不是业务查询。

于是测试改成**相对比较**，让噪声自己抵消：

```
订单号：  有标记连发 10 次 → Com_select +1
          每次先删标记再发 → Com_select +11
          差 10  ⇒ 真的省了 10 次查询 ✓
```

> **教训：用全局计数器做断言，必须先搞清楚里面混了什么。**
> 绝对值不可靠时，用"有 vs 无"的相对差 —— 噪声会自己消掉。

## 3. P3.2 击穿：只放一个人去查

### 3.1 问题长什么样

库存缓存按"房型 + 月份"分桶，TTL 是 24 小时。某个热门房型的桶一过期：

```
100 个请求同时 HGET miss
→ 100 个都去查一次同样的 SQL
```

`HSETNX` 保证了它们**不会互相覆盖**（这是 P1 做对的），但没阻止"100 次重复查询"。

### 3.2 做法

```
抢到锁    → 自己查库、填缓存、放锁
没抢到    → 说明别人正在查：边等边看"写好没"，写好了立刻去重试
等超时了  → 退化成纯数据库路径（P0 那条路，结果仍然正确）
```

**加锁是为了性能，不是为了正确性** —— 所以**拿不到锁应该放行，而不是拒绝服务**。这一点在代码注释里写死了。

### 3.3 锁的粒度：跟查询的粒度对齐

锁是 `房型 + 日期区间`。因为 `loadRangeFromDb` 是用**一条 SQL** 查整个区间的，锁太细就变成"抢好几把锁"，还得处理加锁顺序防死锁。**锁的粒度和它保护的东西要对上。**

### 3.4 ★ 释放锁必须比对 token

分两步（先 GET 比对、再 DEL）是错的：

```
1. 我的锁 TTL 到期，Redis 自动删掉了它
2. 另一个实例抢到了同名锁（token 是它的）
3. 我执行 DEL —— 删掉了【别人的锁】
```

这一下就把互斥彻底破坏了，而且**不会有任何报错**。所以比对和删除必须写在同一个 Lua 脚本里（Redis 的 Lua 是原子执行的，中间插不进别的命令）。

### 3.5 ★ 这把锁不能用来扣库存

代码注释里特意写明了它的能力边界：

| 有 | 没有 |
|---|---|
| 互斥、过期自动释放（防持有者挂掉）、安全释放 | 自动续期、可重入、公平性、Redlock 多节点容错 |

所以它只配用在"短、不重入、偶尔失效也不出事"的地方 —— 补缓存正好符合（两个人同时补也不会写坏，因为 `HSETNX`）。

**扣库存绝不能靠这种锁**：那需要严格互斥，用条件 `UPDATE` 才是对的（判断和执行在一条 SQL 里，比锁更可靠）。

### 3.6 返工一：等待策略

第一版是"死睡 150ms 就放弃"。实测发现**单飞等于白做**：

```
本项目数据库走 SSH 隧道，一次查询要几百毫秒
→ 等待者在持有者填完之前就全放弃了 → 全都退化成直接查库
```

改成**"边等边看"**：每轮先检查"最后一天"有没有写进去（持有者按日期升序写，最后一天出现就等于写完了），写完立刻走，最多等 40 × 50ms = 2 秒。

所以等待**不是固定开销**，而是"最多 2 秒、写完就走"。

### 3.7 返工二：指标又被污染了

`Com_select` 这次**彻底不能用**了：

```
并发 10 个 → Com_select +93     ← 比预期还大
```

原因：里面混着驱动噪声，而我这一轮加的 `NOT_SUPPORTED`（见 §4）**恰好会让它变多**。

改成开 `general_log` **直接数 `FROM room_inventory` 出现几次**，噪声归零：

```
串行 10 次  → 查库存表 1 次
并发 10 次  → 查库存表 1 次     ← 单飞生效
```

> 同一类坑踩了第二次，而且这次是**我自己的改动污染了自己的指标**。

## 4. ★ 那个死锁：并发一来，它就露头了

这一节是 P3 里最值得记录的事，因为它**跟缓存毫无关系**。

### 4.1 它是怎么被发现的

P3.2 第一次跑并发测试（10 个请求同时抢 3 间房），结果是：

```
HTTP 200 × 2     409 × 6     其它 × 2      ← 那 2 个是 500
```

日志里：

```
org.springframework.dao.DeadlockLoserDataAccessException
### Cause: Deadlock found when trying to get lock; try restarting transaction
### The error may involve RoomInventoryMapper.tryOccupy
```

### 4.2 现场是什么样

`SHOW ENGINE INNODB STATUS` 把真相摆得很清楚：

```
事务A: HOLDS S lock (uk_roomtype_date)  /  WAITING FOR X lock   ← 同一行
事务B: HOLDS S lock (uk_roomtype_date)  /  WAITING FOR X lock   ← 同一行
```

翻译成人话：

> 两个人都只是**"看了一眼"**那张纸（共享锁 S），现在都想**把它撕下来改写**（排他锁 X）。而规则是"必须没人在看，才能改"。于是两人互相等对方先松手 —— 谁也动不了。

### 4.3 那个共享锁是哪来的

来自 `INSERT IGNORE`：

```
INSERT IGNORE INTO room_inventory ...   ← 插入重复键时，InnoDB 会给已存在的那一行留一个共享锁
UPDATE room_inventory SET sold_rooms = ...  ← 同一行，要升级成排他锁
```

**这是教科书级的 "S→X 锁升级死锁"。**

### 4.4 为什么之前从没发现

因为**这个项目所有的测试都是串行的**。

这段代码 **P0 就写好了**，跑了几个月、几十次测试、两百多项断言，一次都没触发。P3.2 加的 150ms 等待只是把时间窗口拉宽了，让潜伏的东西浮上来。

> **并发 bug 不会因为你没测过就消失。** 它只是安静地等着真有并发的那一天。

### 4.5 修法：不是重试，是把根因去掉

把"建库存行"挪到**事务之外**（`InventoryRowPreparer`，`@Transactional(NOT_SUPPORTED)` + autocommit，语句执行完就提交并放锁）。

事务内只剩"按 `stay_date` 升序的 `UPDATE`" —— **所有事务加锁顺序一致，不可能形成等待环**，死锁从根上消失。

修完之后：

```
HTTP 200 × 3     409 × 7     其它 × 0
```

正好卖掉 3 间、不超卖、一个 5xx 都没有。

### 4.6 为什么不用"出错重试"

重试是 MySQL 官方推荐的做法，也能用。但那样等于承认"并发下单本来就会偶尔失败"。

而这个死锁的成因很具体（`INSERT IGNORE` 留下的共享锁 + 同事务内的升级），**去掉它就是真的没有了**。分清"绕过去"和"修掉"，是这一节最想说的。

顺带说一句：改成"事务外建行"之后，如果下单最后失败回滚，那些行会留下来 —— 但它们只是 `sold_rooms = 0` 的空行，本来就该存在，无害。

### 4.7 副作用：为什么需要一个单独的类

`createBooking` 本身是 `@Transactional` 的。如果在**同一个类**里调一个标了 `NOT_SUPPORTED` 的方法，会被"自调用"绕过代理，传播行为**不生效** —— 所以 `InventoryRowPreparer` 必须是另一个 Bean。

> 这个坑 P2 也踩过（`expireTimeoutBookings` 在类内部 `this.expireBooking()` 循环，导致 `@Transactional` 失效）。

## 5. P3.3 雪崩：让过期时间错开

### 5.1 问题长什么样

所有库存缓存键都是**懒加载**的：第一次被访问时才创建、同时设过期时间。

如果 TTL 是个固定值，那么**在同一段时间被创建的一批键，会在同一段时间一起过期**。冷启动后集中访问、或者一次性重建一批房型，就会造出这种"同生同死"的批次。

### 5.2 做法

```
TTL = 基础值 + random(0, 抖动上限)
默认  86400 + random(0, 3600)  =>  24h ~ 25h 之间随机
```

一批键的过期时间就被摊到一个小时里，而不是砸在同一秒。

**刻意用"加"而不是"加减"**：抖动只可能让缓存活得更久，绝不会把刚填好的缓存提前弄没。

### 5.3 怎么证明它生效了

关键断言不是"能返回 200"，而是**这批键的 TTL 各不相同**：

```
hotel:inv:{rt:2003}:2026-12   TTL=89692
hotel:inv:{rt:2002}:2026-12   TTL=86742
hotel:inv:{rt:2004}:2026-12   TTL=86999
...（共 12 个）

TTL 取值个数 = 12（12 个全不同）   极差 = 3256 秒
```

**为什么"各不相同"才是关键**：这 12 个桶是在同几秒内创建的。没有抖动的话，它们的 TTL 会**完全相等**——那就等于"到点一起失效"。所以这条断言是"抖动真的生效"的直接证据。

### 5.4 顺带修了一个"客户端错却回 500"

写测试时我用 GET 调了 POST 的接口，收到 **500 而不是 405**。追下去发现：`GlobalExceptionHandler` 的兜底 `@ExceptionHandler(Exception)` **把 Spring MVC 自己的异常全吞成了 500**。

补了四个处理器：

| 异常 | 原来 | 现在 | 场景 |
|---|---|---|---|
| `HttpRequestMethodNotSupportedException` | 500 | **405** | 用错方法 |
| `MethodArgumentTypeMismatchException` | 500 | **400** | `GET /booking/availability` 命中了 `/booking/{bookingId}`，把 `"availability"` 当订单号转 `Long` |
| `HttpMessageNotReadableException` | 500 | **400** | 请求体 JSON 坏 |
| `HttpMediaTypeNotSupportedException` | 500 | **415** | Content-Type 不对 |

其中第二条最有意思：它不是"方法不支持"，而是**路径变量类型转换失败** —— 因为 `/booking/{bookingId}` 这个路由把 `availability` 当成了订单号。

> 这条也是"测试不止验证功能"的例证：一个写错的测试请求，顺手暴露了 4 个 API 缺陷。

## 6. P3.4 改价：失效才是缓存真正的难点

### 6.1 为什么要先加一个改价接口

P3.1~P3.3 都是"读多写少"的缓存。但缓存加完之后**真正难的是"数据改了，缓存怎么失效"**。

而这个项目之前**根本没有改价格的接口** —— 价格缓存加了也永远不需要失效，这个最重要的教训就演示不出来。

所以顺序是：**先加改价接口 → 再给价格加缓存 → 才能真实验证失效。**

### 6.2 价格缓存长什么样

```
key    hotel:price:{rt:2001}:2027-02   (Hash，和库存同样按"房型+月"分桶)
field  2027-02-24
value  400.00   ← 这天的价格
       "-"      ← 这天查过了、确实没有价格日历
```

**那个 `-` 是刻意的**：如果只存"有价格的天"，那"这天没价格"和"这天没缓存"在 Redis 里就一模一样 → 查一个没有价格日历的日期会每次都回源查库（穿透）。**和 P3.1 的 tombstone 同一个思路。**

TTL 也带抖动（默认 `600s + random(0,120)`）。

### 6.3 改价：先写库，再**删**缓存

```
POST /booking/hotel/price/update
{"roomTypeId":2001,"stayDate":"2027-02-24","price":500.00}
→ {oldPrice, newPrice, cacheInvalidated}
```

**删而不是更新缓存**：更新会被并发写覆盖成旧值；删掉则是"下次读的人自己去库里拿最新的"。

### 6.4 一处我没有隐瞒的竞态

```
1. 请求 A 发现某天没缓存 → 去查库（读到旧价 400）
2. 改价接口把库改成 500 → 删缓存
3. 请求 A 把刚读到的 400 写回缓存        ← 缓存里就成了旧价
```

彻底解决要加版本号或"延迟双删"。这里用**较短的 TTL（10 分钟）兜住** —— 最多错 10 分钟。对"改了要尽快生效、但错一会儿不出大事"的价格数据，这个取舍是合理的。

**写进注释和测试注释里，不假装它不存在。**

## 7. 三个毛病的对照（收口）

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| **一句话** | 问不存在的东西 | 一个热点刚过期 | 一大批同时到期 |
| **本项目的解法** | 记住"查过了没有"，60 秒 | 抢锁，只放一个人查库 | TTL 加随机抖动 |
| **代码位置** | `AbsentCache` | `DistributedLock` + `loadWithSingleFlight` | `cacheTtl()` |
| **兜底** | TTL 短，记错了 60 秒自愈 | 等超时就退化成纯数据库路径 | 抖动只加不减，不会缩短寿命 |
| **怎么验证的** | 相对计数：省了 10 次查询 | 10 个并发只查 1 次库 | 12 个桶 12 个不同 TTL |
| **失败了会怎样** | 数据库被无意义查询占满 | 数据库被一个热点打爆 | 数据库被打爆 |
| **会不会丢数据** | 不会 | 不会（拿不到锁就放行） | 不会 |

**三者共同的底线**：缓存出任何问题，业务都得能继续跑（退化成慢，而不是坏）。

### 8.2 按"三个毛病"的顺序看

**穿透** —— `AbsentCache`：

```
:55   isAbsent()      查过没有
:65   markAbsent()    记下来（60 秒）
:83   forget()        主动忘掉（一般靠 TTL 自然过期）
```

**击穿** —— `DistributedLock` + `InventoryCacheService`：

```
DistributedLock:63    tryLock()               SET NX EX，返回 token
DistributedLock:87    unlock()                走 Lua，token 对不上就不删
```

## 10. 踩过的坑

按"花了多久才搞明白"排序。

### ① 并发死锁（见 §4）

`INSERT IGNORE` 留下共享锁 + 同事务内 `UPDATE` → S→X 升级死锁。**P0 就埋着，几个月没被发现，因为所有测试都是串行的。**

### ② 指标被自己污染（两次）

- P3.2：`Com_select` 里混着 JDBC 的 `SELECT @@session.transaction_read_only`
- P3.4：我新加的 `NOT_SUPPORTED` 让这类语句**变多了**，绝对值得出反结论

最终都改成"打开 `general_log` 数特定表名的语句" —— 噪声归零。

### ③ 守护断言抓住了我自己

给测试写常量时我命名成 `$BASE = 86400`，撞上了公共库的 `$script:Base`（API 地址）—— **PowerShell 变量名不区分大小写**。

P3.1 加的运行时守卫立刻报错：

> 「公共库的 `$script:Base` 被覆盖了，现在的值是 '86400'。别用 `$base` / `$Base` 当变量名」

以前同类错误的症状是"**所有请求 HTTP -1**"，要查半天；这次直接指名道姓。

同类碰撞这是第 4 次（前三次是 `$fail`、`$R`/`$Rd` 别名、`$base`）。**三行守卫代码，把一类"看起来像服务挂了"的故障变成了一句话。**

### ④ 字符串里的 ASCII 双引号（5 次）

中文句子里写 `"这样"`，会把外层字符串截断。更麻烦的是有一种情况**语法完全合法**：

```powershell
"...": "a" - "b"      ← 被当成减法
→ Cannot convert value ... to type "System.Int32"
```

语法检查抓不到，要运行时才炸。现在 `check-syntax.ps1` 除了查 BOM、查语法，还查**每行双引号是否成对**（排除注释行和 here-string 定界符）。

### ⑤ 测试自己写错的几处

| bug | 教训 |
|---|---|
| 冷缓存测量前自己先 quote 了一次 | 缓存已经热了，量不到"回源"那一次 |
| `$d2 = D102` 当成了"第二个住宿夜" | 那是**离店日**，当然不在 `nightPrices` 里 |
| 还原价格时还原成"运行时刻的当前值" | 应该还原成**种子价** —— 否则上次跑的污染会被当成基准传下去 |
| 探测 2003 的桶，却重建了 2001 | 断言"抖动没重新随机"其实是自己搞错了对象 |

**这些都不是业务代码的问题，但每一条都会让测试"看起来像功能坏了"。**

## 11. 边界

| 没有 | 说明 | 为什么 |
|---|---|---|
| **本地缓存（Caffeine）** | 只有 Redis 一层 | 本次决定不做。本地缓存真正的难点是"多实例间怎么失效"，单实例下它永远不会失效、反而演示不了那个难点 |
| **布隆过滤器** | 穿透用的是"空值标记" | 零依赖、够用；布隆过滤器在**删除数据后要重建**，成本更高 |
| **锁的自动续期 / 可重入 / Redlock** | 只有最小可用版 | 补缓存是短临界区，不需要 |
| **分布式定时任务** | `@Scheduled` 多实例会各跑一遍 | 单实例；真上多实例时要处理（靠条件 UPDATE 兜着不会错，但会重复空转） |
| **改价竞态的彻底解决** | 用短 TTL 兜底 | 见 §6.4，诚实地说这是没解决的 |
| **缓存预热** | 库存/价格都是懒加载 | 可选 |

## 12. 通往 P4

P4 = **鉴权 + Agent**。

| 位置 | 现在 | P4 之后 |
|---|---|---|
| 身份 | `userId` 由请求体传入（**不可上线**） | 登录 + Token，用户身份从凭证里取 |
| 权限 | 无 | 只能操作自己的订单（越权校验） |
| 新增 | — | 分类路由（用户想干什么）+ BookingAgent（多轮）+ 人工确认（HITL） |

**P4 第一个要想清楚的事**：现在所有接口都靠"信任前端传的 `userId`"。加上鉴权之后，`userId` 必须从 Token 里取，**而且所有已有的测试都要跟着改**（它们现在都是硬编码 `userId=9001`）。

这是 P4 会碰到的第一个连锁改动，比 P3 的任何一件事影响面都大。
